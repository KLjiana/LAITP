## 1. 声明、依据与边界

### 1.1 本文要回答的问题

检测不是分类的“多类别变体”：一张图片可以有任意数量、位置和类别的框，模型输出是集合而不是单个标签，因此输入输出语义、标注、数据清单、结果载荷和固定样本比较都需要独立的格式定义。本文只回答三件事：

1. 检测任务如何用现有清单结构和版本规则表达（P1 契约扩展草案）；
2. 每图标注、数据集清单、预测结果和固定样本参考结果长什么样（P2 标注/结果格式草案）；
3. 评审与落地的顺序、退出条件，以及需要 lead 先决定的问题。

本文**不回答**模型选型、训练参数、精度指标、K230/K210 转换工具链和课堂预算；这些属于 [检测课可行性规划](detection-feasibility.md) 的 P3～P9，当前同样未实现。

### 1.2 强制声明（未激活）

1. **草案、未激活**：本文所有字段、JSON 示例、版本号和阈值均未进入任何生产路径。P1 评审通过不等于契约生效；正式引入必须按 [模型接口与产物契约](model-contract.md) 第 7 节升版，并按该文第 9 节同步文档、JSON Schema、生产方、消费方和测试。
2. **分类契约 `1.0` 冻结**：现有分类清单字段、标签语义、预处理/后处理规则、固定样本格式、版本兼容行为与校验器策略均不因本文改变。已发布的分类 `1.0` 产物包必须继续被新版本接收方接受。
3. **没有生效的检测 Schema**：`schemas/` 的正式加载路径只有 `model-manifest.schema.json`、`dataset-manifest.schema.json`、`project.schema.json`、`message-envelope.schema.json`；检测标注、检测数据清单与检测结果的**草案** Schema 位于独立目录 `schemas/detection/`（未激活、不在加载路径上）。`model-manifest.schema.json` 中已有的 `object_detection` 任务枚举、`raw_detections`/`detections` 输出语义、`device` 执行方与板端平台字段是此前预留的**结构占位**，不代表受支持（与 [检测课可行性规划](detection-feasibility.md) 第 1.2 节一致）。
4. **校验器仍按不支持拒绝**：当前实现只接受 `image_classification`、执行方 `host`、分类输出语义和 ONNX Runtime 主机平台。按现有代码与 [契约校验说明](contract-validation.md) 第 3、4 节，检测相关输入的预期行为如下：

| 输入（示例） | 当前预期行为 | 说明 |
| --- | --- | --- |
| 结构落在当前 Schema 内、但 `task` 为 `object_detection` 的清单 | `CONTRACT_TASK_UNSUPPORTED` | 版本与结构通过后、进入任务检查时拒绝 |
| 清单声明 `contract_version` 为 `1.1` 或更高次版本 | `CONTRACT_VERSION_UNSUPPORTED_MINOR` | 当前接收方只声明支持 `1.0` |
| 清单声明主版本 `2.0` | `CONTRACT_VERSION_UNSUPPORTED_MAJOR` | 未知主版本直接拒绝 |
| 执行方为 `device` 或 `model` | `CONTRACT_EXECUTOR_UNSUPPORTED` | 当前只验证 `host` |
| 板端平台（`k230`/`k210`）产物 | `CONTRACT_BOARD_UNSUPPORTED` | 需要实物、固件与板端运行时验证 |
| 使用本文示例中的新后处理步骤或未知字段 | 先按 `CONTRACT_SCHEMA_INVALID` 拒绝 | 当前 Schema 的后处理步骤枚举、字段白名单和 `additionalProperties: false` 不包含本文候选字段 |

这些拒绝是**预期行为，不是缺陷**；不能为了“先跑起来”而放宽校验器或把检测字段塞进分类 `1.0`。

5. **引入前置条件**：检测任务至少需要新的契约版本、任务专属必填语义、后处理步骤定义、数据集清单版本、项目格式版本和消息协议版本；任何一项缺失时，检测产物只能作为草案材料存在，不能标记为可用。版本线分别维护，不共用一个版本号（见第 2.1 节与第 5 节 Q1）。

### 1.3 需要遵守、但本文不重复的强制条款

以下规则来自 [模型接口与产物契约](model-contract.md)，检测同样适用；本文只引用，不复制全文：

- **完整产物包与不可变**：`manifest.json` 是唯一入口，权重、标签、固定样本和参考结果作为整体交付；已发布产物不可原地修改，新训练/导出/转换生成新 `artifact_id`（第 2 节）。
- **文件摘要与路径**：包内文件必须列出相对路径、用途和 SHA-256；禁止绝对路径、目录穿越和包外符号链接；SHA-256 只证明文件与清单一致，不证明来源可信（第 2 节）。
- **整体加载与切换**：模型、标签、预处理及后处理配置整体加载和切换，不能分别替换（第 2 节）。
- **交接点校验**：训练发布、电脑加载、模型转换、板卡部署分别执行适用校验；转换成功不等于板端验证通过（第 5 节）。
- **固定样本与阈值**：固定样本用于交接冒烟，不能代替代表性测试集；验收阈值必须在运行前按任务、精度和设备冻结并版本化，不得看到失败后放宽（第 8 节）。
- **版本兼容**：改变字段含义、必填结构或处理语义时升级主版本；兼容的可选扩展升级次版本；接收方声明支持范围，未知主版本拒绝；不自动猜测或隐式迁移旧模型（第 7 节）。
- **消息协议**：UTF-8 按行 JSON、信封字段、任务身份、迟到与重复消息处理按第 6 节；协议版本与模型契约版本独立维护。

## 2. 检测任务标识与产物包草案

### 2.1 任务与版本线

检测任务类型固定为字符串 `task: "object_detection"`。它是 [模型接口与产物契约](model-contract.md) 第 3 节任务枚举中的预留值，但**语义尚未定义**：只有任务名不能说明输出是原始检测头还是已解码结果，也不能说明框格式、坐标空间和处理执行方。

引入检测必须同时决定下列版本线。它们独立维护，不能用同一个版本号掩盖全部变化：

| 版本线 | 现状 | 检测引入时（候选） |
| --- | --- | --- |
| 模型契约版本 | `1.0` | `1.1`（次版本）或 `2.0`（主版本），见 Q1；本文示例暂用 `1.1` 仅作示意 |
| 数据集清单版本 | `1.0`（仅分类，每样本一个 `class_id`） | 建议 `2.0`：样本结构从“一图一类别”改为“一图多框 + 标注引用” |
| 项目格式版本 | `1.0`（`task` 只允许分类） | 需新版本以保存检测任务与标注引用；本草案不展开字段 |
| 消息协议版本 | `1.0` | 候选次版本（例如 `1.1`），与模型契约版本独立 |
| 标注格式版本 | 无（未实现） | 由数据集清单 `2.0`/项目格式声明；是否给每图 JSON 加版本字段见 Q7 |

规则：

- 分类产物继续声明 `contract_version: "1.0"`；检测产物必须声明评审通过的新版本。接收方必须同时声明对旧版本和新版本的支持范围。
- 未知主版本直接拒绝；较新次版本只有在接收方声明支持、且所需能力全部可用时才接受；不允许“忽略未知字段继续运行”。
- 不自动把分类项目或分类清单迁移为检测项目。若复用分类课图片，应新建检测项目并重新标注，保留来源说明（见 [检测课可行性规划](detection-feasibility.md) 第 3.3 节）。

### 2.2 manifest 字段：复用与新增

检测清单继续使用 [模型接口与产物契约](model-contract.md) 第 3 节的顶层结构；P2 Schema 草案需要在现有字段上增加检测语义，而不是另建一套清单。下表只列与检测相关的变化，未列字段沿用契约原文。

| 字段 | 处置 | 检测草案要求 |
| --- | --- | --- |
| `contract_version` | 复用 | 候选新版本；当前 `1.0` 没有检测语义，当前校验器拒绝新版本（见 1.2） |
| `artifact_id` | 复用 | 每次训练或转换重新生成；不得复用分类或旧检测产物 ID；已发布包不可原地修改 |
| `task` | 复用枚举 | 固定 `object_detection`；必须与数据集清单、项目任务一致 |
| `provenance` | 复用 | `dataset_manifest_sha256` 指向检测数据集清单 `2.0` 的摘要；转换产物还必须有 `source`（来源 `artifact_id` 与来源清单 SHA-256） |
| `files` | 复用 | 模型、标签、固定样本、参考结果、阈值、校准清单都列入 `files` 并给出 SHA-256；不得列 `manifest.json` 自身 |
| `model` | 复用 | 首版仍为 ONNX；格式、opset 和实际张量由导出与校验确认；板端格式字段留到转换阶段定版 |
| `inputs` | 复用，明确语义 | **输入尺寸**由 `inputs[0].shape` 声明（如 `[1, 3, 640, 640]`），不另设独立尺寸字段以免出现双重来源；必须声明 dtype、NCHW/NHWC、RGB/BGR、像素范围；量化模型另需 `quantization` |
| `preprocessing` | 复用容器，扩展语义 | 必须声明执行方、有序步骤、缩放方式（含 `letterbox` 补边颜色/位置/取整规则）、归一化公式与反算回原图所需参数；当前运行时显式拒绝 `letterbox`，扩展前不能加载 |
| `outputs` | 复用枚举，补充语义 | `meaning` 为 `raw_detections` 或 `detections`，必须唯一明确；需补充框格式（`xyxy`/`cxcywh` 等）、坐标空间、置信度计算方式、类别轴/字段位置等语义（候选字段名待 P2 冻结） |
| `postprocessing` | 复用容器，新增步骤 | 新增 `decode_detections`、`nms`、`map_boxes_to_source` 等步骤；每步参数显式，禁止默认值；必须声明 NMS 是否在模型图内、执行方及“只执行一次”的归属 |
| `labels` | 复用 | `labels.json` 仍是 UTF-8 有序字符串数组，下标即 `class_id`，加载时不得排序或重编号；背景/忽略类不得写入 `labels.json`，如模型含此类必须显式声明映射；单类时 `count` 下限与现有“至少 2 类”的冲突见 Q2 |
| `runtime` | 复用 | 首版电脑端为 ONNX Runtime、`windows-x64`、`onnxruntime-cpu`；**版本范围**写在 `runtime.version_range`；板端运行时、固件与模型格式不在本草案定义，留到 P6/P7 定版 |
| `validation` | 复用，扩展参考结果 | 固定样本 `samples[].path` 与 `reference_output` 结构见第 4.5 节；阈值放在 `validation.thresholds` 引用的版本化文件；固定样本至少覆盖单目标、多目标和贴边目标（数量与内容待 P2/P3 定） |
| `conversion` | 暂不扩展 | 检测转换记录、量化与板端字段由 P6/P7 另行定义，避免在契约版本未定时提前承诺 |

补充要求：

- 清单不能只写“YOLO 输出”或“标准后处理”这类含义不明的描述；必须给出可复现的参数与坐标约定。
- 同一操作只能由约定的一方执行。若模型图已含解码或 NMS，清单必须声明，外部程序不得重复执行；若由外部执行，模型图必须声明不含该步骤。
- 字段名是候选，P2 Schema 草案可以改名；但**语义覆盖范围**必须满足 [模型接口与产物契约](model-contract.md) 第 4.2 节的全部强制问题。

### 2.3 manifest 示例片段（候选，非可加载）

下面只展示检测相关片段，省略未变化的 `provenance`、`files`、`model` 等字段。**该片段不是可加载清单**：其中的新版本号、输出字段和 `decode_detections`/`nms`/`map_boxes_to_source` 步骤均不在当前 Schema 中，当前校验器会拒绝；数值与形状仅用于说明结构，不是模型或课堂参数。

```json
{
  "contract_version": "1.1",
  "task": "object_detection",
  "inputs": [
    {
      "name": "images",
      "shape": [1, 3, 640, 640],
      "dtype": "float32",
      "layout": "NCHW",
      "color_space": "RGB"
    }
  ],
  "preprocessing": {
    "executor": "host",
    "source_pixel_range": [0, 255],
    "steps": [
      {
        "op": "resize",
        "width": 640,
        "height": 640,
        "mode": "letterbox",
        "interpolation": "bilinear",
        "pad_color": [114, 114, 114],
        "pad_position": "center"
      },
      {
        "op": "normalize",
        "formula": "(pixel * scale - mean) / std",
        "scale": 0.00392156862745098,
        "mean": [0.485, 0.456, 0.406],
        "std": [0.229, 0.224, 0.225],
        "channel_order": "RGB"
      },
      { "op": "transpose", "from": "HWC", "to": "CHW" },
      { "op": "add_batch_dimension", "axis": 0 }
    ]
  },
  "outputs": [
    {
      "name": "pred",
      "shape": [1, 8400, 7],
      "dtype": "float32",
      "meaning": "raw_detections",
      "box_format": "cxcywh",
      "box_space": "model_input",
      "score_semantics": "objectness_x_class"
    }
  ],
  "postprocessing": {
    "executor": "host",
    "steps": [
      {
        "op": "decode_detections",
        "output": "pred",
        "class_count": 2,
        "strides": [8, 16, 32],
        "box_format": "cxcywh",
        "box_space": "model_input"
      },
      {
        "op": "nms",
        "algorithm": "greedy",
        "iou_threshold": 0.45,
        "score_threshold": 0.25,
        "class_agnostic": false,
        "max_detections": 100
      },
      {
        "op": "map_boxes_to_source",
        "from": "model_input",
        "to": "source_image",
        "letterbox_scale_mode": "min",
        "pad_position": "center",
        "rounding": "round_half_away_from_zero",
        "clamp": true
      }
    ]
  },
  "labels": { "path": "labels.json", "count": 2 },
  "runtime": {
    "runtime": "onnxruntime",
    "version_range": ">=1.23.0,<2.0.0",
    "platform": "windows-x64",
    "device": "cpu",
    "required_capabilities": ["onnxruntime-cpu"]
  },
  "validation": {
    "samples": [
      {
        "name": "sample-01",
        "path": "validation/sample-01.png",
        "reference_output": "validation/expected-01.json"
      }
    ],
    "thresholds": { "path": "validation/thresholds.json" }
  }
}
```

说明：

- 输入尺寸 `640×640` 由 `inputs[0].shape` 与 `preprocessing.resize` 共同表达，两者必须一致；源图尺寸不在清单中硬编码，由运行时解码后确定并用于框映射。
- `labels.count` 必须与 `labels.json` 实际数量、输出类别维一致；示例取 2 只表示结构，不表示课堂类别数。
- 量化产物必须声明实际输入输出 dtype、scale、zero point 和逐通道轴，不能假设仍是 `float32`；当前电脑运行时尚未实现量化输入输出，这一点不因清单字段存在而改变。

### 2.4 产物 ID、SHA-256、固定样本与版本规则

- **产物 ID**：训练格式、ONNX 导出格式和转换/量化格式分别使用独立 `artifact_id`，保留来源关系；导出不得复用训练记录 ID，转换不得复用来源包 ID。失败或取消的临时产物不发布、不加载、不登记（[模型接口与产物契约](model-contract.md) 第 2、5 节）。
- **SHA-256**：清单 `files` 中的每个载荷文件都必须有相对路径、用途和摘要；固定样本图片、参考结果、阈值配置、校准清单都必须列入。摘要用于发现替换和错配，不证明标签语义正确；标签顺序和参考结果仍需固定样本与训练记录共同确认（契约第 2、8 节与 [契约校验说明](contract-validation.md) 第 5 节）。
- **固定样本**：检测产物包至少包含一组固定样本和电脑端生成的参考结果。参考结果不是人工标注，必须由电脑端运行时按清单参数计算；人工标注只用于代表性测试集的效果评估。固定样本只做交接冒烟，不能代替测试集指标（契约第 8 节；匹配规则见第 4.5 节）。
- **版本兼容升级规则**：完全按契约第 7 节执行，本文不重复。检测特有的判断是：仅增加新任务名和可选检测字段属于候选次版本扩展；一旦改变分类字段含义、必填结构、单类下限、后处理执行方结构或固定样本比较语义，就必须按主版本处理。所有版本变化必须同步 Schema、生产方、消费方和测试；未完成同步前不允许接收方“先接受再报警”。
- **当前拒绝行为**：即使检测清单结构合法，当前接收方仍按 1.2 节拒绝；不能用关闭校验、跳过任务检查或伪造分类标签绕过。

## 3. 标注格式草案

### 3.1 每图 JSON

检测标注采用**每图一个 JSON 文件**，与图片分开保存，UTF-8 无 BOM；保存时先写临时文件再整体替换，取消或失败不留下半写标注。最小结构如下（字段名为候选）：

```json
{
  "image": "relative/path.png",
  "width": 640,
  "height": 480,
  "boxes": [
    { "class_id": 0, "x": 12, "y": 20, "w": 100, "h": 80 }
  ]
}
```

| 字段 | 要求 |
| --- | --- |
| `image` | 相对路径，基准为项目 `data/` 数据根；必须与数据集清单中该样本的 `path` 一致（规范化后）；禁止绝对路径、盘符、反斜杠、`..` 和空路径段；不靠目录遍历猜测对应关系 |
| `width` / `height` | 图片解码后的实际像素尺寸，整数且大于 0；必须与实际解码结果一致，不一致直接拒绝，不能静默缩放 |
| `boxes` | 数组，可以为空数组（是否允许作为负样本待 Q6）；字段必须存在，缺字段不等于空标注 |
| `boxes[].class_id` | 整数，从 0 开始，必须小于类别表长度；只存 ID，不写类别名；类别顺序只存在于项目类别表与 `labels.json`，加载时不得排序 |
| `boxes[].x` / `y` | 框左上角坐标，整数像素 |
| `boxes[].w` / `h` | 框宽、高，整数像素，必须大于 0 |

标注中不写模型预测结果；把预测框回灌成标注必须经过人工确认。未知字段按 Schema 拒绝（避免拼写错误被忽略），不提供“宽松模式”静默丢弃。

### 3.2 坐标与合法性约定

| 规则 | 草案约定 |
| --- | --- |
| 原点与方向 | 图片左上角为 `(0, 0)`，x 向右、y 向下 |
| 单位 | 原图像素（导入并转 PNG 后的实际解码尺寸），不是模型输入尺寸，也不是归一化坐标 |
| 边界含义 | 右边界与下边界**不包含**，即必须有 `0 <= x`、`0 <= y`、`w > 0`、`h > 0`、`x + w <= width`、`y + h <= height` |
| 类型 | `width`、`height`、`class_id`、`x`、`y`、`w`、`h` 都必须是整数；布尔值、浮点数、字符串、`NaN`/`Inf` 一律拒绝 |
| 越界 | 越界、零面积、负值一律拒绝；不得静默 clamp、取整或丢弃 |
| 取整 | 标注界面按整数像素取整，取整规则固定并写入文档；保存前显示取整后的结果，避免“看起来在界内、实际越界” |
| 最小尺寸 | 过小框的硬性下限待 P2 评审（建议 `w >= 2`、`h >= 2` 像素，未冻结）；低于下限时应在界面提示放大或剔除并说明原因 |
| 重复框 | 不按格式错误拒绝；数据检查阶段把同类、`IoU` 超过约定阈值的框报为“疑似重复”，要求人工确认，不自动删除 |
| 重叠 | 不同类别的重叠框合法；同类遮挡/重叠是正常样本，不按重复处理 |
| 空标注 | **规则待定（Q6）**：允许空 `boxes`（负样本）还是要求每图至少一个框，必须在 P2 定稿前决定；在决定前，实现方不得自行选择某种解释作为默认行为 |
| 每图版本字段 | 本草案不把 `annotation_version` 写入每图 JSON；标注格式版本由数据集清单/项目格式统一声明。是否改为每图独立版本字段见 Q7 |

图片导入沿用现有“转 RGB PNG、按内容 SHA-256 去重”的做法；图片与标注通过数据集清单中的路径、图片摘要、标注路径和标注摘要绑定。重命名图片时同步重命名标注，删除图片时同步删除标注；图片或标注摘要不一致时，训练和测试必须拒绝，不能继续。

### 3.3 数据集清单扩展草案

检测数据集清单候选版本为 `2.0`（未激活）。与分类 `1.0` 的核心差异是：样本不再有单一 `class_id`，改为引用每图标注，并把图片摘要、图像尺寸与框数量纳入清单。候选结构以草案 Schema `schemas/detection/dataset-manifest-2.0-draft.schema.json` 为准（未激活），本节只保留字段说明；候选结构如下（**不是可加载清单**；当前数据集校验器只接受 `1.x`、`task: image_classification` 和每样本一个 `class_id`，本片段会被拒绝）：

```json
{
  "schema_version": "2.0-draft",
  "dataset_version": "2.0-draft",
  "dataset_id": "ds-20261119-0001",
  "created_at": "2026-11-19T10:00:00+08:00",
  "classes": ["水杯", "书本"],
  "splits": {
    "train": {
      "samples": [
        {
          "image": "images/batch-1/001.png",
          "annotation": "annotations/batch-1/001.json",
          "sha256": "…64 位小写十六进制…",
          "width": 640,
          "height": 480,
          "box_count": 1,
          "capture_batch": "batch-1"
        }
      ]
    },
    "val": { "samples": ["…"] },
    "test": { "samples": ["…"] }
  }
}
```

> **口径：以草案 Schema 为准（未激活）。** 上面代码块中的 `"…"` 与中文摘要占位不是合法值，完整且可校验的样例见 `tests/fixtures/detection/dataset-manifest-valid.json`；字段名、必填性、版本标记和划分结构以 `schemas/detection/dataset-manifest-2.0-draft.schema.json` 为准，本节与 Schema 不一致时按 Schema 修正。

规则草案：

- **样本引用**：`image`、`annotation`、`sha256`、`width`、`height`、`box_count` 必填（结构见草案 Schema），`capture_batch` 可选；`sha256` 为 64 位小写十六进制图片内容摘要。校验时读取标注并核对：标注中的 `image` 与样本 `image` 一致、`width`/`height` 与图像实际尺寸一致、每个 `class_id` 在 `classes` 范围内、`box_count` 与标注框数一致。图片可解码性和摘要按现有数据检查原则执行。标注文件自身的摘要字段尚未纳入草案 Schema，是否必需待评审。
- **目录引用**：标注实际存放到 `data/annotations/`（测试集为 `data/test-annotations/`）；清单记录相对路径和图片摘要，**不要求**靠文件名约定推断对应关系。文件名与目录组织方式见 Q7。
- **划分**：`splits` 仍为 `train`/`val`/`test` 三个对象，样本放在各自 `samples` 数组中（不再逐样本写 `split` 字段）；按图片和采集批次划分，同一批次只能出现在一个划分；同一图片的所有框随图片整体进入同一划分；`test` 冻结后不参与训练、调参或阈值选择。划分由清单决定，不从目录名推断。
- **空标注样本**：`box_count` 为 0 在当前草案 Schema 中结构合法（`minimum: 0`），用于表达空标注；是否允许作为负样本仍取决于 Q6，若允许，必须单独统计负样本比例，并确保负样本不会掩盖漏标问题。
- **类别表**：`classes` 有序、唯一、下标即 `class_id`；类别改名不改变 ID，调整顺序视为不兼容变更。单类检测是否允许见 Q2。
- **版本**：`schema_version` 固定为 `2.0-draft`；可选 `dataset_version` 出现时也只能是 `2.0-draft`。文档早期候选值 `2.0` 未激活，正式版本号命名、是否需要 `2.1` 之类的兼容扩展由 Q1/P2 决定；改变样本必填结构必须按主版本处理。
- **任务字段**：当前草案 Schema 顶层不包含 `task`；检测任务身份由项目格式与模型产物声明，清单是否增加 `task` 字段待评审。
- **追溯**：训练记录的 `dataset_manifest_sha256` 指向该清单，清单本身必须被训练产物保存一份副本；标注内容变化后旧训练记录含义不变。

### 3.4 与现有分类数据布局的关系

现有分类布局（[数据与运行基线](data-and-runtime-baseline.md) 第 2 节）保持不变：

```text
学生项目/
  data/
    dataset-manifest.json
    images/<类别>/<采集批次>/<图片>
    test-images/<类别>/<采集批次>/<图片>
```

检测项目建议在同一项目根结构下使用批次镜像布局（候选，未实现）：

```text
学生项目/                              # project.json 中 task = object_detection
  project.json
  data/
    dataset-manifest.json              # 检测数据集清单 2.0 候选
    images/<采集批次>/<图片>.png        # 检测图片不按类别分目录
    annotations/<采集批次>/<图片>.json  # 每图标注
    test-images/<采集批次>/<图片>.png
    test-annotations/<采集批次>/<图片>.json
```

兼容关系：

| 类别 | 内容 |
| --- | --- |
| 复用 | 项目根与 `project.json` 的角色；`data/`、`runs/`、`exports/`、`validation-runs/`、`logs/` 的布局；采集批次命名规则；`classes` 有序表与 `class_id` 语义；相对路径、摘要、原子保存和产物包规则 |
| 新增 | `data/annotations/`、`data/test-annotations/`；检测数据集清单 `2.0`；项目格式中的检测任务与标注引用；检测导入、标注、训练与测试入口 |
| 禁止 | 在 `labels.json` 之外用文件名/目录名承载类别；把分类 `1.0` 清单改义来存框；同一项目混用分类与检测清单；自动把分类项目“升级”为检测项目；用旧产物 ID 冒充检测产物 |

- 分类项目继续使用 `data/images/<类别>/<批次>/`，不受检测布局影响；检测项目使用 `data/images/<批次>/`，因为一张图片可同时含多个类别，无法用类别目录唯一归类。
- 旧程序打开检测项目时必须按任务/格式版本明确拒绝，而不是忽略标注或猜测任务；不存在自动迁移。若复用分类课图片，应新建检测项目并重新标注、重新训练、重新导出。
- 本文只给出数据集清单草案；`project.json` 的检测任务字段、模型引用与标注引用属于项目格式升版内容，由 P2 另行起草，避免一次改动过多版本线。

## 4. 预测与结果输出草案

### 4.1 检测结果结构

电脑测试与消息协议的检测结果使用扁平框列表（候选结构，坐标空间必须显式声明）：

```json
[
  {
    "class_id": 0,
    "label": "水杯",
    "confidence": 0.93,
    "x": 120,
    "y": 80,
    "w": 200,
    "h": 260
  }
]
```

| 字段 | 要求 |
| --- | --- |
| `class_id` | 整数，必须是 `labels.json`/项目类别表的有效下标 |
| `label` | 显示用冗余字段，必须与 `class_id` 对应；**不得**用 `label` 做映射，映射只认 `class_id` |
| `confidence` | 0～1 的浮点数，含义与阈值口径由清单声明；不同后端不能各自定义“置信度” |
| `x` / `y` / `w` / `h` | 框坐标，类型与边界约定同标注（整数像素、左上角、右/下不含）；坐标空间必须显式声明 |
| 结果级 `coordinate_space` | 在结果对象整体声明，不在每个框中重复；最终展示/比较使用 `source_image`（原图像素） |

结果对象还应携带 `artifact_id` 与图片引用，便于界面和日志核对归属；空结果仍是合法结果。

### 4.2 坐标空间、排序、NMS 与空结果

- **坐标空间**：候选约定为 `source_image`（原图像素，与标注同一套约定）。模型输入坐标（`model_input`）或缩放后图像坐标（`resized_image`）只能作为调试/中间结果出现，必须显式声明，不能与最终结果混用，也不能一部分框用输入坐标、一部分用原图坐标。若最终采用归一化坐标，必须另行定义原点和边界含义并重做本草案（Q5）。
- **排序**：结果按 `confidence` 降序；同分时用确定性次序（建议 `class_id` 升序，再按 `x`、`y`、`w`、`h`）保证可复现。排序不是匹配依据，固定样本比较必须顺序无关。
- **NMS 执行方与参数**：NMS 是否在模型图中执行、由电脑端还是板端执行，必须在清单 `postprocessing` 中声明；参数（算法、IoU 阈值、分数阈值、是否 class-agnostic、最大检测数）以清单为唯一来源，运行时不得使用隐含默认值。模型图已含 NMS 时外部不得重复执行；板端若裁剪候选数或最大检测数，必须作为不同配置重新验证。NMS 实现版本应写入验证记录。
- **空结果**：无检测时返回 `"detections": []`。不得省略字段、不得写 `null`、不得用错误代替“没有目标”；CLI 仍以成功退出（退出码 0），信封仍发送 `result` 消息。固定样本期望为空时，只有空列表通过。
- **阈值回显**：结果中可以附带供诊断的阈值快照，但加载、校验和固定样本比较必须以产物包清单和冻结的阈值配置为准，不能用结果里的阈值反向修改行为。

### 4.3 消息信封 payload 草案

检测结果复用 [模型接口与产物契约](model-contract.md) 第 6 节的信封字段；`payload` 候选结构如下（候选协议版本 `1.1` 仅示意，协议版本独立于模型契约版本）：

```json
{
  "protocol_version": "1.1",
  "request_id": "req-20261119-0001",
  "project_id": "proj-20261119-0001",
  "task_id": "task-20261119-0001",
  "message_type": "result",
  "sequence": 3,
  "artifact_id": "art-20261119-0001",
  "payload": {
    "operation": "predict",
    "artifact": {
      "artifact_id": "art-20261119-0001",
      "manifest_path": "exports/art-20261119-0001/model-package/manifest.json",
      "manifest_sha256": "…64 位小写十六进制…"
    },
    "image": "data/images/batch-1/001.png",
    "coordinate_space": "source_image",
    "detections": [
      {
        "class_id": 0,
        "label": "水杯",
        "confidence": 0.93,
        "x": 120,
        "y": 80,
        "w": 200,
        "h": 260
      }
    ]
  }
}
```

约束：

- 检测结果用 `detections`，分类结果继续用 `predictions`；两者按任务/操作互斥，不能在同一 payload 中混用，也不能把检测框塞进 `predictions`。
- 信封中的 `artifact_id` 与 `payload.artifact.artifact_id` 必须一致；旧任务、迟到消息和重复序号的处理沿用 [任务协议与父进程](task-protocol.md) 第 2 节，不因检测任务改变。
- 当前 `schemas/message-envelope.schema.json` 的 `resultPayload` 只包含 `predictions` 且 `additionalProperties: false`，检测 payload 会被 `ENVELOPE_SCHEMA_INVALID` 拒绝；协议升版与 Schema 扩展必须走同样的评审流程。
- 协议版本与模型契约版本独立维护；不能因为检测契约升版就自动改变所有消息版本，也不能复用旧 `predictions` 字段含义。

### 4.4 CLI JSON 草案

电脑端单图预测的 CLI JSON 候选结构如下（沿用现有 `ok` + 结构化字段的风格；**当前 CLI 没有检测实现**）：

```json
{
  "ok": true,
  "command": "predict",
  "package": "exports/art-20261119-0001/model-package",
  "artifact_id": "art-20261119-0001",
  "image": "data/images/batch-1/001.png",
  "input_size": [640, 640],
  "coordinate_space": "source_image",
  "detections": [
    {
      "class_id": 0,
      "label": "水杯",
      "confidence": 0.93,
      "x": 120,
      "y": 80,
      "w": 200,
      "h": 260
    }
  ]
}
```

- 成功但无目标时 `ok` 仍为 `true`、`detections` 为空数组，退出码 0；失败时返回稳定错误码与阶段，退出码 1。
- `input_size` 是模型输入尺寸（来自清单），不是原图尺寸；原图尺寸可由图片解码获得。两者不能混用，框坐标按 `coordinate_space` 解释。
- CLI 字段名是候选；P4 实现前需与现有 `predict` 命令的错误码和输出风格对齐，不能仅凭本文判定接口已可用。

### 4.5 固定样本参考结果与匹配规则

固定样本参考结果由电脑端运行时按产物包参数生成，不是人工标注；候选结构如下：

```json
{
  "sample": "validation/sample-01.png",
  "input_tensor_sha256": "…64 位小写十六进制…",
  "coordinate_space": "source_image",
  "detections": [
    {
      "class_id": 0,
      "confidence": 0.93,
      "x": 120,
      "y": 80,
      "w": 200,
      "h": 260
    }
  ]
}
```

匹配规则草案（算法版本、阈值和容差必须写入版本化阈值配置，并与产物 ID、清单摘要绑定）：

1. **坐标空间先统一**：参考结果与当前结果都必须声明 `coordinate_space`；若不同，先按清单声明反算到统一的原图像素空间再比较，不能直接比较模型输入坐标。量化/letterbox 的取整规则必须按清单执行。
2. **类别匹配**：`class_id` 必须完全一致；`label` 仅用于显示，不参与匹配。类别顺序错位会使全部匹配失败，而不是被当成部分命中。
3. **顺序无关**：两侧都先按置信度降序；从最高置信度开始，为每个参考框寻找尚未匹配、同类且 `IoU` 不低于阈值的检测框，取 `IoU` 最大者匹配；每个检测框和参考框最多匹配一次。结果列表顺序不影响通过与否。
4. **IoU 阈值**：阈值从冻结的阈值配置读取。候选默认值：固定样本交接冒烟 `IoU >= 0.5`；同一模型训练端与 ONNX Runtime 的浮点一致性可更严格（例如 `IoU >= 0.99` 并限制置信度绝对差）；量化后按 Q8 另行冻结。本文数值只是候选，不是验收结论。
5. **误差与遗漏/多余**：匹配上的框比较坐标误差和置信度误差；未匹配的参考框计为遗漏，未匹配的检测计为多余。通过条件、坐标容差、置信度容差和量化后容差都在阈值配置中冻结，失败后不得临时放宽。
6. **空结果**：参考结果为空时，只有当前结果也为空才通过；缺字段、`null` 或解析失败按失败处理。
7. **覆盖范围**：固定样本至少覆盖单目标、多目标、贴边目标，无目标场景按 Q6 结论处理；固定样本只做交接冒烟，不能代替代表性测试集上的效果评估（契约第 8 节）。
8. **可追溯**：比较算法版本、阈值配置、产物 ID、清单摘要、运行环境和固定样本摘要写入验证记录，便于复现和区分“算法差异”与“实现错误”。

## 5. 待决问题（Q1–Q8）

以下问题需要 lead/课程负责人决定；在决定前，相关字段只能保持草案状态。

| 编号 | 问题 | 影响 | 本草案暂定写法 / 建议 |
| --- | --- | --- | --- |
| Q1 | 检测契约用次版本（如 `1.1`）还是主版本（如 `2.0`）？数据集清单、项目格式、消息协议是否分别升版？板端扩展是否再单独升一次？ | 决定所有 Schema 的兼容策略、接收方支持范围和拒绝行为 | 建议电脑端检测走次版本、分类 `1.0` 冻结；数据集清单用 `2.0`、项目格式与协议各自独立升版；板端在 P6 结论后单独定版。若单类下限、执行方结构等必须改变分类既有约束，则改用主版本 |
| Q2 | 单类检测是否正式支持？类别数下限是多少？ | 当前清单标签 `count` 下限为 2、项目与数据清单 `classes` 也至少 2；课堂很可能只教 1 类 | 建议允许检测任务 1 类，但必须作为任务条件约束（分类仍至少 2 类），不能塞入无意义类别；改动下限需按 Q1 的版本策略处理 |
| Q3 | 后处理（解码、NMS、映射回原图）执行方放在哪里？模型图是否允许含 NMS？是否需要逐阶段声明执行方？ | 决定清单结构、电脑端与板端的一致性验证方式 | 首版建议模型图不含 NMS、后处理全部由 `host` 执行；板端 `device` 执行留到 P6/P7。若采用逐阶段执行方，需要在清单中显式声明每一段，不能让“默认执行方”产生歧义 |
| Q4 | NMS 参数归谁所有、是否允许用户调整？ | 影响清单权威性、固定样本复现和课堂可操作性 | 建议参数只来自产物包清单，运行时不得有隐式默认值；界面可以显示但不能静默修改。若允许用户调阈值，必须作为新配置记录并重新验证，不能与已发布产物的固定样本结论混用 |
| Q5 | 结果与标注使用原图像素还是归一化坐标？ | 影响标注、结果结构、匹配算法、量化和取整误差 | 本文按“原图像素、整数、右/下不含”暂定，与标注同一套约定；若改归一化，必须重新定义原点、边界含义和取整规则，并同步修改标注、结果和参考结果 |
| Q6 | 空标注（无目标图片）是否允许？如何表示、比例上限多少、是否进入固定样本与测试集？ | 影响负样本、误检评估、数据集清单 `box_count` 和训练数据检查 | 本文要求 `boxes` 字段始终存在，但空数组是否合法待定；建议允许并按比例记录，但必须单独统计，且不能把漏标当负样本。决定前实现方不得自行选择默认解释 |
| Q7 | 标注文件如何命名与对应？是否给每图标注加版本字段？ | 影响目录布局、重命名/删除同步、大小写敏感性和可移植性 | 建议 `annotations/<采集批次>/<图片主名>.json`，同时保留 `image` 字段做交叉校验；`labels.json` 的路径与数量由模型清单固定，不另起命名。是否加入每图 `annotation_version` 需与数据集清单版本一起决定 |
| Q8 | 量化后允许的框偏移、IoU 下降和置信度误差是多少？由谁在何时冻结？ | 决定转换/量化一致性检查和板端验收是否通过 | 本文不冻结数值；建议沿用[检测课可行性规划](detection-feasibility.md) 第 6.3 节的候选区间，在 P7 运行前由工程与课程负责人共同冻结，写入版本化阈值配置并与产物绑定，不得看到失败结果后放宽 |

### 6.2 退出条件未满足时的限制

在顺序 0～3 未完成前：

- 不把任何检测 Schema 加入生效的 `schemas/` 加载路径，不修改校验器默认策略，不登记检测能力；
- 不编写检测训练、导出、推理或 UI 生产代码；
- 不生成“检测模型包”“检测数据集清单”作为可用产物；
- 不在状态报告、课堂材料或验收清单中写“检测已支持/已通过”；当前唯一可报告的是“草案待评审”。

顺序 4 之后即使已经实现局部链路，也必须保持“电脑端通过不等于板端通过、转换成功不等于板端验证通过”的边界；任何固定样本或阈值变化都要重新记录证据（契约第 5、8 节）。

### 6.3 本文档已做与未做的检查

- 已做：阅读现有契约、可行性、校验、项目与推理文档，核对当前 `schemas/` 文件、校验器任务/版本/执行方/板端拒绝行为，并运行 `scripts/check_docs.py` 做文档链接与现有文档统计口径检查。

## 7. 给 lead 的决策提示

建议 lead 先决定 **Q1/Q2/Q3/Q6/Q7**：

- Q1（契约版本与各版本线）决定后续所有 Schema 的兼容策略；
- Q2（单类检测下限）决定类别表、标注和数据集清单能否覆盖课堂最常见的 1 类场景；
- Q3（后处理执行位置与阶段声明）决定检测清单结构和电脑/板端一致性验证方式；
- Q6（空标注是否允许）决定标注、数据清单和评估的负样本规则；
- Q7（标注文件命名与版本字段）决定 `annotations/` 的目录约定和重命名/删除同步规则。

这五项确定后，P2 才能把标注、数据集清单和结果格式草案收敛为可评审的 Schema 草案。Q4、Q5、Q8 可随 P3/P6 实测细化；其中 Q5 的像素/归一化选择会影响标注与结果格式，建议在 P2 评审时一并确认。
