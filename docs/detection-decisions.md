## 3. 决策建议（Q1–Q8）

以下每节结构固定：问题（契约草案原文）、背景与现状、建议选项、理由、备选与代价、影响文件与后续工作、若已决定应如何记录。“建议选项”是推荐，不是决定。

### 3.1 Q1：契约版本与各版本线

**问题（契约草案原文）**：检测契约用次版本（如 `1.1`）还是主版本（如 `2.0`）？数据集清单、项目格式、消息协议是否分别升版？板端扩展是否再单独升一次？

**背景与现状**

- 当前模型契约 `1.0` 的分类链路已实现：清单、ONNX、`labels.json`、固定样本、SHA-256、严格校验、执行方限 `host`（可行性规划第 1.2 节）。
- [模型接口与产物契约](model-contract.md) 第 7 节规定：改变字段含义、必填结构或处理语义时升主版本；兼容的可选扩展升次版本；接收方声明支持范围，未知主版本拒绝，较新次版本仅在明确允许且能力受支持时接受；不自动猜测或隐式迁移。
- `schemas/model-manifest.schema.json` 已有 `object_detection`、`raw_detections`/`detections`、执行方 `device`、板端平台与 `conversion` 等枚举/字段，但只是**结构占位**，校验器仍拒绝（草案第 1.2 节、契约校验说明第 3、4 节）。
- 四条格式线的现状：模型契约 `1.0`；数据集清单 `1.0`（`task` 只允许分类，每样本一个 `class_id`，类别数至少 2）；项目格式 `1.0`（`task` 只允许分类，类别数至少 2）；消息协议 `1.0`（结果载荷只有 `predictions`）。
- 检测引入后必然变化：数据集清单样本结构从“一图一类别”变为“一图多框 + 标注引用”，必填结构变化；项目格式要表达检测任务、条件下限与标注引用；模型清单新增检测输出语义、后处理步骤与固定样本参考结构；消息协议新增检测结果载荷。
- 板端扩展（kmodel、`device`、板端运行时/固件、检测量化字段）依赖 P6/P7 工具链实测，现在无法确定最终形态。

**建议选项**

采用 **Q1-A：分线、以次版本为主、结构变化用主版本**：

| 版本线 | 建议目标版本 | 级别 | 说明 |
| --- | --- | --- | --- |
| 模型契约 | `1.1` | 次版本 | 仅新增检测任务语义、检测输出语义、检测后处理步骤、固定样本参考结构；分类 `1.0` 字段、语义和校验行为完全不变 |
| 数据集清单 | `2.0` | 主版本 | 样本必填结构从“单类别”变为“多框 + 标注引用 + 图片/标注追溯字段”，属主版本变化 |
| 项目格式 | `2.0` | 主版本 | 默认按主版本处理；若 P2 证实项目格式只需新增可选字段和 `task` 枚举、不改变既有必填结构，才降为 `1.1` |
| 消息协议 | `1.1` | 次版本 | 新增检测结果载荷变体；分类 `predictions` 载荷原样保留 |
| 标注格式 | 不单独起顶层版本 | — | 由数据集清单 `2.0`（或项目格式）声明标注格式版本；每图标注不设版本字段（Q7） |
| 板端契约 | P6 结论后另定 | 待定 | 只新增可选字段/枚举则 `1.2` 次版本；若改变现有字段含义或必填结构则 `2.0` 主版本，并显式双读、禁止自动迁移 |

次版本成立的前提（任一不满足则改主版本 `2.0`）：

1. 分类 `1.0` 产物包的接受/拒绝行为逐条不变（含标签下限、执行方、预处理/后处理、固定样本比较）；
2. 所有检测新约束按 `task` 条件生效，不改变分类包的必填结构、字段含义或默认行为；
3. 旧接收方对声明 `1.1` 的包显式拒绝（预期 `CONTRACT_VERSION_UNSUPPORTED_MINOR`），不得静默降级解析；
4. 新接收方同时声明支持 `1.0` 与 `1.1`，并拒绝未知主版本；
5. 文档、Schema、生产方、消费方、测试五处同步完成（契约第 9 节），未同步完不得让接收方“先接受再报警”。

**理由**

1. 契约第 7 节的标准就是“语义变化升主版本、兼容扩展升次版本”；检测对模型清单是新增任务和可选语义，分类语义不需要改，按标准应优先次版本。
2. 分类 `1.0` 已实现且已有测试与本机验证记录，破坏它会带来无需承担的回归和课堂产物兼容成本（可行性规划第 2.6 节建议 1）。
3. 数据集清单和项目格式的结构变化是真实的，必须独立升主版本，不能用模型契约的次版本号“顺带”掩盖。
4. 四条版本线独立维护，能按各自变化节奏升级；`2.0` 留给真正改变已发布分类语义的变更（例如将来统一类别下限、改执行方结构、改固定样本比较语义）。
5. 板端字段现在承诺版本号属于无依据预设；按契约第 9 节，检测及 K230 扩展应在电脑端链路之后再接入。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 全部一次性升 `2.0` | 模型契约、数据集清单、项目格式、协议全部主版本 | 边界最清晰 | 现有 `1.0` 接收方全部拒绝；需要双读、迁移说明和更大回归面；并没有必须改分类语义的理由，属过度升版 | 不推荐 |
| B2 全部塞进 `1.1` 次版本 | 连数据集清单也沿用 `1.x` 改义 | 版本号少 | 违反“改必填结构升主版本”；同一版本下分类/检测语义不一致，旧清单可能被误读；不可接受 | 不可接受 |
| B3 检测另起并行契约 | 单独一套 detection-contract-1.0 和校验器 | 互不影响 | 破坏“`manifest.json` 唯一入口”和 JSON Schema 单一来源；两套产物包分叉，维护和错配风险最大 | 不推荐 |
| B4 等 P6 板端结论再定电脑端版本 | 先不写版本号，等工具链 | 少一次决策 | 阻塞 P2 结构定稿与 P4/P5 开发，把唯一可先行的电脑端链路拖到硬件之后 | 不推荐 |

- 明确“数据集清单、项目格式、消息协议各自独立升版”的负责人和完成时点；
- 更新草案第 2.1 节和 P1 退出条件，把“已决策”与“已实现”分开表述。

### 3.2 Q2：单类检测与类别数下限

**问题（契约草案原文）**：单类检测是否正式支持？类别数下限是多少？

**背景与现状**

- `schemas/model-manifest.schema.json` 的 `labels.count` 下限为 2；分类数据集清单与项目格式的 `classes` 下限也是 2。
- 检测数据集清单 `2.0` 草案已按 `minItems: 1` 允许单类（草案文档第 3.3 节、`schemas/detection/README.md` 第 6 节），但明确标注“是否正式允许未冻结，实现方不得自行决定”。
- 课堂最可能只教 1 类：可行性规划第 1.3 节建议 1～3 类，第 3.2 节“开发最小”类别数为 1，且标注工作量随类别数增加。
- 可行性规划 R8 与可研 Q3 已把“单类触及至少 2 类下限”列为风险；用假类别或背景类凑数会违反“背景类不得混入 `labels.json`”的规则（可行性规划第 2.2、2.4 节）。

**建议选项**

采用 **Q2-A：检测任务允许单类，分类任务保持至少 2 类，按任务条件约束**：

- 检测任务类别数下限为 **1**：`labels.json` 为长度 1 的有序数组，`class_id = 0`；检测数据集清单与检测项目格式的类别表 `minItems: 1`。
- 分类任务保持 **至少 2 类**：不因检测放宽而改变分类清单、分类数据集和分类项目的既有行为。
- 类别数为 0 一律非法（空类别表不是“单类”）；不允许用“背景”“无目标”“忽略”等占位类别凑数，也不允许把背景/忽略类写入 `labels.json`；模型若含背景/忽略类必须在清单中显式映射。
- 单类检测的固定样本、验证集、测试集仍需覆盖该类（类别覆盖检查不能因单类退化而跳过）；单类 AP/mAP 的评估口径由 P4 评估实现确定并写入验收配置。

**理由**

1. 课堂最简检测场景就是“找一个东西”，单类能显著降低采集与标注成本（可行性规划第 3.2 节）。
2. 不改分类规则就没有分类回归，符合 Q1 的“分类 `1.0` 冻结”策略。
3. 检测数据集清单 `2.0` 草案已经按 1 类设计，改动成本最低；难点只在模型清单与项目格式的条件约束。
4. 单类不改变检测定义：仍是多实例检测，只是类别集合大小为 1；背景/忽略类的语义必须显式声明，不能靠“只有一类所以默认”的隐式解释。
5. 假类别会污染标签、训练与评估，是三类方案中后果最坏的。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 检测也要求至少 2 类 | 沿用全局 `minItems: 2` | Schema 零改动 | 课堂必须凑第二类或强制两类采集，增加课时与标注量；诱导假类别，违反标签规则 | 不推荐 |
| B2 全局改为至少 1 类 | 分类与检测都允许单类 | 规则统一 | 改变分类既有语义与项目/数据校验，需主版本并重跑分类回归；分类课原本要求至少 2 类，教学规则变化大 | 不推荐 |
| B3 允许 0 类 | 纯背景/异常检测 | 理论可扩展 | 超出 M3 检测范围（检测要有目标类别），与“背景类不写入标签”冲突 | 不采纳 |
| B4 只在开发样例允许 1 类 | 正式课堂仍要求 2 类 | 看似折中 | Schema 必须有一个确定下限，实际等于 B1 或 Q2-A，留模糊会阻碍实现 | 不推荐 |

**影响文件与后续工作**

- `schemas/model-manifest.schema.json`：`labels.count` 按任务条件（分类 ≥2、检测 ≥1），通过 `allOf`/条件分支实现，分类样例保持原行为；
- 检测数据集清单 `2.0` Schema：保持 `classes` `minItems: 1`；分类数据集清单 `1.0` 不变；
- 项目格式新版本：`classes` 按任务条件，检测项目允许 1 类；
- 标签校验与评估：长度 1 合法、空标签/背景标签拒绝、单类指标口径；
- 测试：检测 1 类包结构合法、分类 1 类包仍被拒绝、背景类标签被拒绝、检测项目/数据集 1 类合法。

**若已决定应如何记录**

- 记录中写明“任务条件约束”而不是“全局放宽”，并列出受影响的三个 Schema（模型清单、数据集清单、项目格式）；
- 写明背景/忽略类不得进入 `labels.json` 的规则不变；
- 若决定仍要求至少 2 类，必须同时记录课堂如何满足第二类（真实类别，不得占位），并评估对课时的影响。

### 3.3 Q3：后处理执行方与图内 NMS

**问题（契约草案原文）**：后处理（解码、NMS、映射回原图）执行方放在哪里？模型图是否允许含 NMS？是否需要逐阶段声明执行方？

**背景与现状**

- 当前清单的 `preprocessing.executor` 与 `postprocessing.executor` 是**容器级**枚举（`host`/`model`/`device`），后处理步骤只有 `softmax`；校验器只接受 `host` 与分类语义（草案第 1.2 节）。
- 检测后处理至少包含“解码 → NMS → 映射回原图”三个阶段，电脑测试与板端运行可能需要不同执行方（可行性规划第 2.3 节表格）。
- 可行性规划第 2.2 节建议第一版**模型图不含 NMS、不绑定原图坐标**：模型输出原始检测头，解码与 NMS 由清单声明的一方执行；这样模型可同时用于电脑和板端，转换前后差异容易定位。
- 契约强制“同一操作只能由约定的一方执行一次”；模型图已含 NMS 时外部不得重复执行（可行性规划第 2.3 节、草案第 2.2、4.2 节）。
- 板端算力和转换器算子支持是未知项（可行性规划 R3）：图内 NMS 可能提高板端效率，也可能直接导致 nncase 转换失败。
- **本机草案探测证据（2026-11-19，未激活）**：用 `scripts/detection_draft_probe.py`（草案工具，不接入生产）对 torchvision SSDLite320-MobileNetV3-Large（`weights=None`、`weights_backbone=None`、`num_classes=3`，随机初始化）做了一次 CPU 单次探测：opset 17 导出的 ONNX 约 **8.98 MB、1,481 节点、43 种算子**，**不含 `NonMaxSuppression`、无自定义 domain**；onnxruntime 输出 `boxes(128,4)`/`scores(128)`/`labels(128)`，即导出图未包含 NMS/最终筛选，128 行是候选上限（结果见 `artifacts/detection-draft/probe-ssdlite.json`，本机生成、不提交）。**同一轮另运行 fasterrcnn 分支**（`--model fasterrcnn`，条件相同，结果见 `artifacts/detection-draft/probe-fasterrcnn.json`）：opset 17 ONNX 约 **75.94 MB、1,515 节点、53 种算子**，同样**不含 `NonMaxSuppression`、无自定义 domain**，但图含 `If` 与 `RoiAlign`，体积/参数约为 SSDLite 的 8.5 倍，转换风险更高。该证据说明“首版模型图不含 NMS”在两个 torchvision 候选上都可实行；但图含控制流算子 `If`（另含 `NonZero`、`TopK`，fasterrcnn 还有 `RoiAlign`），nncase/K230 是否支持**未验证**；其它候选（如 YOLO）未探测，不能外推。以上为本机单次、随机权重、未训练/未转换/未量化的探测结果，不是检测能力或板端证据，也不构成 Q3 决定。

**建议选项**

采用 **Q3-A：逐阶段声明执行方；首版模型图不含 NMS，电脑端全 `host`，板端执行方 P6/P7 再定**：

1. **清单结构从检测第一版起支持逐阶段执行方**：`postprocessing` 用有序步骤表达（`decode_detections`、`nms`、`map_boxes_to_source`），每一步必须显式声明 `executor`（`host` 或 `device`），不使用“容器默认值 + 阶段继承”的隐式规则；若保留容器级字段，只允许作为“所有阶段相同”的显式简写，校验器仍按阶段核对。
2. **首版模型图不含 NMS，也不含“反算回原图”的绑定**：模型输出 `raw_detections`（或明确声明已解码但仍在模型输入坐标空间的结果）；NMS 在模型外执行。导出与转换时核对 ONNX 算子清单，含 `NonMaxSuppression` 等后处理算子即拒绝，不靠“看起来没问题”放行。（本机 SSDLite 与 fasterrcnn 草案探测均未发现图内 NMS，见上；其它候选未探测，不能外推。）
3. **“只执行一次”是强制校验**：清单必须声明每个后处理阶段位置，校验器检查阶段齐全、不重复、与图内声明不冲突；任一阶段缺 `executor`、重复执行或使用默认参数都拒绝。
4. **首版支持矩阵**：电脑端（P4/P5）支持 `host` 全链；板端（P6/P7）支持 `device` 全链或经验证的逐阶段混合；`model` 仅用于声明图内后处理，首版不允许含 NMS 的图，其他图内步骤按 P6/P7 结论再放开。
5. **板端执行方后置**：不在 P1/P2 承诺板端必须是 `device` 还是混合；P6 工具链与 P7 量化结论出来后，按 Q1 的板端版本线补记一次决策（可能是 Q3 的子决策），并重新验证固定样本。

**理由**

1. 契约的“一次且仅一次”“参数唯一来源”要求清单能表达每个阶段的归属；容器级单一执行方在电脑/板端分化后会表达不了。
2. 首版电脑端只需要 `host`，逐阶段声明不会增加首版能力负担，却避免 P6 因结构不足再升版。
3. 模型图不含 NMS 与可行性规划第 2.2 节的建议一致，也降低转换器算子风险（R3）。
4. 电脑与板端使用同一组参数、各自执行阶段，是固定样本一致性比较能成立的前提。
5. 板端执行方式依赖工具链实测，现在承诺会制造无证据约束。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 保持容器级执行方 | 整条后处理链只有一个执行方 | 结构小、首版简单 | P6 若出现“图内 NMS + 外部映射”或混合阶段就无法表达，只能再升版 | 可接受但扩展性差，不推荐 |
| B2 首版就允许图内 NMS | NMS 写进模型图 | 板端可能更快 | NMS 算子常不受转换器支持，行为差异难定位；外部“只执行一次”校验更难；排除该选项更稳 | 不推荐 |
| B3 后处理全部固定 `host` | 板端也把结果传回电脑算 | 电脑测试简单 | 板端无法独立离线运行，违背 M3 板端目标 | 不推荐 |
| B4 后处理全部固定 `device` | 电脑也模拟板端实现 | 两端一致 | 电脑端不能用 ONNX Runtime 直接验证，固定样本交接冒烟不可行 | 不推荐 |

**影响文件与后续工作**

- `schemas/model-manifest.schema.json`：检测后处理步骤、逐阶段 `executor`、模型图后处理声明；含 NMS 图的拒绝规则；
- 校验器：阶段顺序、执行方支持矩阵、“只执行一次”检查，以及对应的稳定错误码（命名待 P2 定）；
- 导出/转换：ONNX 算子清单检查；转换记录保存“图内/图外后处理”声明；
- P4/P5 检测运行时与界面：按阶段实现解码/NMS/映射，固定样本比较绑定同一份清单；
- P6/P7：转换器与板端运行时能力实测；若板端要求图内 NMS 或改变阶段归属，触发再决策并重新验证；
- 测试：缺 `executor` 拒绝、重复 NMS 拒绝、声明冲突拒绝、分类 `softmax` 行为不变。

**若已决定应如何记录**

- 记录中写明三条硬规则：首版模型图不含 NMS；后处理逐阶段声明执行方；电脑端 `host`、板端执行方式 P6/P7 再定；
- 写明“图内含 NMS 的包在首版被拒绝”及对应错误码（待实现时定名）；
- 把板端执行方作为 Q3 的**未决子项**登记（负责人、P6/P7 决策点、再评估条件），不能以“结构已预留”视为已决定。

### 3.4 Q4：NMS 参数归属与运行时可调性

**问题（契约草案原文）**：NMS 参数归谁所有、是否允许用户调整？

**背景与现状**

- 检测结果对分数阈值、IoU 阈值、`class_agnostic`、`max_detections` 很敏感：同一权重、不同阈值会得到不同检测集合，固定样本比较和验收结论都会变化。
- 契约要求处理语义与参数由清单声明、运行时不得使用隐含默认值；固定样本与验收阈值必须在运行前冻结（契约第 4.2、8 节）。可行性规划第 2.3 节要求电脑端与板端使用清单中的同一组参数。
- 当前清单 `postprocessing` 只有 `softmax`，还没有检测参数结构；`validation.thresholds` 目前只有一个 `path` 引用。
- 课堂中教师/学生可能想调阈值看效果（可操作性需求），但调整后固定样本参考结果和验收结论不能自动继承。

**建议选项**

采用 **Q4-A：运行参数唯一来源为产物包清单，运行时不改；调整走派生配置**：

1. **权威来源唯一**：NMS/解码/映射参数只来自产物包 `manifest.json` 的 `postprocessing`；运行时和界面不得内置“常用默认值”作为回退，缺参数或参数非法必须拒绝加载/预测。
2. **已发布产物不可在运行时改参数**：界面可只读展示参数；不得静默修改清单或覆盖产物包。
3. **课堂调整走“派生配置”**：若需要尝试不同分数/IoU 阈值，生成新的配置记录（新配置 ID 或派生产物记录），重新生成固定样本参考结果并重新验证；派生配置的验证状态独立，不能继承原产物的“已验证”结论。
4. **运行参数与验收/比较阈值严格分开**：NMS 分数/IoU/最大检测数是运行参数（在清单）；匹配算法版本、匹配 IoU 阈值、坐标/置信度容差是验收/比较阈值（在版本化阈值配置）；两者不得互相替代或互相“借用”。
5. **探索模式边界**：如果 P5 界面提供“临时试阈值”的探索模式，其结果必须标注“非验证结果”，不得作为课堂交付、固定样本结论或验收证据；退出探索模式后恢复清单参数。

**理由**

1. 可复现性：同一产物包在电脑和板端必须得到可比较的结果，参数漂移会让固定样本失去意义。
2. 契约第 4.2、8 节的强制要求，不是可选的易用性偏好。
3. 课堂可操作性与产物不可变并不冲突：用派生配置表达“试阈值”，而不是改既有产物。
4. 验证状态不能自动继承，否则容易出现“调了参数却声称已验证通过”。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 界面可实时调阈值且不落盘 | 拖动滑块看结果 | 教学直观 | 结果不可复现；固定样本、板端一致性和验收都无法成立；只能作为演示 | 仅限“探索模式”，且结论无效 |
| B2 参数硬编码在程序里 | 后端/界面写默认值 | 开发快 | 违反“处理语义必须声明”；电脑/板端参数会漂移；换模型必须改代码 | 不可接受 |
| B3 允许调阈值并放宽验收阈值 | 为通过而调参数 | 省事 | 明确违反契约第 8 节，结论无效 | 明确禁止 |
| B4 完全禁止界面调整 | 参数只读 | 最稳 | 课堂演示不灵活，教师难以解释阈值作用 | 可接受，A 更优 |

**影响文件与后续工作**

- `schemas/model-manifest.schema.json`：检测后处理参数结构（算法、`iou_threshold`、`score_threshold`、`class_agnostic`、`max_detections`、是否按类别分别执行等），必填且无默认；
- 校验器/运行时：参数必填检查、禁止默认值、拒绝时返回稳定错误码；
- P4：派生配置 ID、发布/验证流程与记录格式；
- P5：只读展示、派生配置入口、探索模式标识；
- 验收配置与验证记录：阈值快照与产物 ID/清单摘要绑定；
- 测试：缺参数拒绝、参数改变生成新配置、固定样本重新验证、板端与电脑使用同一清单参数。

**若已决定应如何记录**

- 记录中写明“谁拥有参数”（产物包清单是唯一权威；课程负责人不直接修改已发布产物）；
- 写明调整流程（派生配置 + 新 ID + 重新生成参考结果 + 重新验证）和探索模式边界；
- 写明运行参数与验收阈值是两套文件、两套版本，不得混用。

### 3.5 Q5：原图像素与归一化坐标

**问题（契约草案原文）**：结果与标注使用原图像素还是归一化坐标？

**背景与现状**

- 草案第 3.2、4.2 节暂定“原图像素、整数、右/下边界不包含”；`annotation.schema.json` 的框坐标是整数，`detection-result.schema.json` 的框坐标是数值（允许小数）。
- 草案第 4.1 节正文又写“结果框类型与边界约定同标注（整数像素）”，与 `detection-result.schema.json` 的 `number` 口径**不一致**；第 1.5 节也把字段命名差异列为待收敛项。P2 定稿时必须统一。
- 检测模型内部常用归一化输入或 `cxcywh`/`model_input` 坐标；letterbox 后需要反算回原图（可行性规划第 2.2、2.3 节）。
- 可行性规划第 6.3 节建议坐标比较在**原图像素空间**进行，框角点误差 ≤1 像素（待冻结）。
- **本机草案探测证据（2026-11-19，未激活）**：同一 SSDLite 草案探测（随机权重、输入 1×3×320×320、opset 17）的 onnxruntime 原始输出为 `boxes(128,4)`，数值范围 **0.0～320.0**，不在 `[0,1]` 内，也不是原图像素；`scores(128)` 在随机权重下恒为 0.3333，`labels(128)` 为 1～2（torchvision 把 `num_classes` 的 0 类当背景，本机未建立 `labels.json` 映射）。同一轮 fasterrcnn 草案探测的 `boxes(100,4)` 同样在 **0.0～320.0**（输入像素尺度；输出名已按模型实际字典顺序声明为 `boxes`/`labels`/`scores`，可按名称对应类型，见可行性规划 §4.5“输出命名说明”）。这说明模型原始输出坐标空间必须由清单显式声明，且必须在模型外映射/反算回原图；本机**未验证**映射、反算或统一像素口径。该证据支持“模型输入坐标只作内部/调试信息”的方向，但不决定 Q5，也不代表检测能力已实现。

**建议选项**

采用 **Q5-A：统一原图像素，标注整数、结果浮点，归一化只作内部中间量**：

1. **标注**：原图像素、整数、左上角原点、x 向右 y 向下、右/下边界不包含（`x + w <= width`、`y + h <= height`），与现有 `annotation.schema.json` 和草案第 3.2 节一致。
2. **运行时结果/参考结果/消息/CLI**：原图像素、数值**允许小数**（不强制取整），结果对象必须声明 `coordinate_space: source_image`；界面展示可以格式化，但存储与比较使用未取整值，**不得**把展示取整结果当比较依据。
3. **模型输入坐标只作内部/调试信息**：`model_input`、`resized_image`、归一化坐标必须显式标记，不得混入最终结果，不得一部分框用输入坐标、一部分用原图坐标。（本机 SSDLite 与 fasterrcnn 草案探测所见原始 `boxes` 数值均为 0.0～320.0，与 320×320 输入同量级，正是模型输入尺度而非原图像素，见上；映射未验证。）
4. **比较规则**：标注与结果的匹配在浮点原图像素空间计算 IoU 和坐标误差，容差在阈值配置中冻结（例如建议 1 像素，P7 前冻结）；不要求逐位相同。
5. **P2 收敛动作**：把草案第 4.1 节“类型与边界约定同标注（整数像素）”修正为“标注整数、结果浮点原图像素”，并在正文与 Schema 之间建立明确对应；若 P2 最终决定结果也必须整数，则按备选 B2 处理并同步改 Schema 与容差。

**理由**

1. 与现有草案主体和 `annotation.schema.json` 一致，改动最小。
2. 学生和教师能直接理解“第几个像素”，画框、复核和课堂讲解都直接；归一化坐标需要反复换算。
3. 量化/letterbox 误差评估本来就在原图空间进行（可行性规划第 6.3 节）。
4. 标注整数避免半像素和越界歧义；结果浮点避免二次取整损失，比较仍可按容差进行。
5. 归一化会引入“标注单位、结果单位、匹配阈值单位”三套口径，错配风险最高。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 归一化坐标 `[0,1]` | 标注、结果都用相对坐标 | 与模型内部一致、分辨率无关 | 标注需浮点或高精度取整；原点/边界/越界规则重定义；固定样本容差改相对值；像素容差与量化误差需换算；现有 Schema/文档大改；课堂画框仍按像素，界面多一层误差 | 不推荐作为首版 |
| B2 结果也强制整数 | 结果取整到整数像素 | 序列化简单、显示整齐 | 每框最多 0.5 像素系统误差；letterbox 反算取整规则必须冻结；参考结果/量化比较容差需重定；所有输出必须一致 | 可选，作为 A 不通过时的备选；需同时冻结取整规则 |
| B3 混合坐标空间 | 部分结果保留 `model_input` | 调试方便 | 草案第 4.2 节与可行性规划第 2.2 节已明确禁止混用；会造成坐标错配与固定样本误判 | 明确禁止 |

**影响文件与后续工作**

- `schemas/detection/annotation.schema.json`（整数，保持）、`schemas/detection/detection-result.schema.json`（小数语义明确化）；
- 草案第 3.2、4.1、4.2、4.5 节口径修正；CLI JSON、消息协议 `1.1` 的检测载荷；
- P4 预处理 letterbox 与反算实现、匹配/评估实现；P7 量化一致性比较；P8 板端结果输出；
- 测试：越界、反算、坐标空间声明、混合坐标拒绝、固定样本容差。

**若已决定应如何记录**

- 记录中写明“标注整数原图像素、结果浮点原图像素、`coordinate_space` 必填、比较容差在阈值配置中冻结”；
- 记录两处草案/ Schema 不一致按本决策收敛的结论，并指定 P2 定稿时同步修改的段落；
- 若选择 B2，需同时记录取整规则（如四舍五入到最近整数）和容差，不能只写“结果用整数”。

### 3.6 Q6：空标注与负样本

**问题（契约草案原文）**：空标注（无目标图片）是否允许？如何表示、比例上限多少、是否进入固定样本与测试集？

**背景与现状**

- 草案第 3.1 节要求 `boxes` 字段必须存在，空数组是否合法待定；`annotation.schema.json` 结构上允许 `boxes: []`（未设 `minItems`）；检测数据集清单 `2.0` 草案 `box_count` 最小值为 0。
- 可行性规划第 3.1 节写“无目标图片必须显式写 `boxes: []`，不能缺文件或省略字段；空标注样本可作为负样本，但比例受限并单独统计”；第 3.2 节建议训练负样本占比 0～15%（建议值，未冻结）；可研 Q12 建议允许负样本并记录比例。
- 负样本用于评估和降低误检；但大量空标注可能掩盖学生漏标，让漏标被当成负样本，训练和评估都会失真。
- 固定样本是否包含无目标场景，可行性规划第 2.4 节列为“可选”。

**建议选项**

采用 **Q6-A：允许空标注，但必须显式、可统计、受限**：

1. **表示方式**：`boxes: []`（字段必须存在）；缺文件、缺字段、`null` 都不等于空标注，一律拒绝；检测数据集清单中 `box_count: 0` 必须与标注空数组一致。
2. **用途与划分**：空标注可进入 `train`/`val` 作为负样本；`test` 是否包含空标注由课堂评估场景决定，若包含必须单独报告（否则误检率无法体现）。不允许把未标注图片自动当作负样本。
3. **比例上限**：建议训练集无目标图片占比**默认不超过 15%**（沿用可行性规划第 3.2 节首课建议值；这是数据检查的提示/上限候选，不是验收阈值），并记录实际比例、单独统计；比例是否冻结由 P3 实测与课堂需求决定。
4. **质量与防漏标**：空标注样本需人工确认确实无目标；数据检查对“相邻批次/同类场景突然大量空标注”给出提示，防止漏标被当作负样本。
5. **固定样本与测试集**：固定样本至少包含 1 个无目标场景为**建议**（用于回归误报），固定样本仍以单目标、多目标、贴边为主；若不纳入，必须在阈值配置或验证记录中说明原因。
6. **不改变结构**：`annotation.schema.json` 不加 `minItems: 1`；语义规则（允许条件、比例）由数据检查与文档冻结，而不是靠 Schema 预设结论。

**理由**

1. 负样本是控制误检的常规手段，课堂也需要“没有目标时不要乱报”的评估（可研 Q12）。
2. 显式表示 + 单独统计 + 提示上限，能避免“漏标被当负样本”的污染。
3. 与现有草案和 Schema 的结构兼容，无需结构性改动，只需定语义。
4. 固定样本加一个空场景成本低，能回归误报路径。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 禁止空标注 | 每图至少 1 框，Schema 加 `minItems: 1` | 数据简单，避免漏标污染 | 无法评估误检；训练缺少负样本；课堂“无目标场景”无法保存；结构变更 | 可接受但评估不完整，不推荐 |
| B2 允许但无上限、不单独统计 | 随便空标注 | 最省事 | 漏标污染严重；指标不可解释；误检无法归因 | 不推荐 |
| B3 只在 test 允许空标注 | 训练/验证必须有框 | 可测误检 | 训练仍无负样本，规则不自然，数据管理复杂 | 不推荐 |
| B4 负样本独立成集 | 单独目录/清单 | 数据管理清晰 | 新增目录与清单结构，超出首版最小改动 | 可作为 A 的后续演进 |

**影响文件与后续工作**

- `schemas/detection/annotation.schema.json`（不加 `minItems`）、检测数据集清单 `2.0`（`box_count: 0` 语义）；
- 数据检查：空标注比例、漏标提示、负样本单独统计；
- 训练数据读取：负样本参与训练的方式；评估：无目标图片的指标口径；
- 固定样本与测试集规则；标注界面（空标注展示、保存与确认）；
- 测试：空数组按决策合法、缺 `boxes` 拒绝、`box_count` 一致性、比例超限提示、负样本统计、漏标提示。

**若已决定应如何记录**

- 记录“允许/不允许、表示方式、比例规则（上限、统计口径、是否冻结）、固定样本与测试集是否包含空场景、误检评估口径”；
- 若选择允许，明确“数据检查提示 15%”是建议阈值而不是 Schema 限制，防止实现方把它当成硬拒绝条件；
- 若选择禁止，需同时记录 Schema 变更与对课堂采集指导的影响。

### 3.7 Q7：标注文件命名、对应与版本字段

**问题（契约草案原文）**：标注文件如何命名与对应？是否给每图标注加版本字段？

**背景与现状**

- 草案第 3.3、3.4 节建议检测项目使用 `data/annotations/<采集批次>/<图片主名>.json`，测试集用 `data/test-annotations/<采集批次>/<图片主名>.json`；标注内 `image` 字段做交叉校验。
- `schemas/detection/annotation.schema.json` 有一个**可选** `version` 字段（描述为“取值格式与是否保留为待决问题 Q7”），但草案正文第 3.1 节的结构里没有该字段，第 1.5 节也写“每图版本字段待定（Q7）”——**Schema 与文档不一致，P2 必须收敛**。
- 检测数据集清单 `2.0` 草案样本已必填 `image`、`annotation`、`sha256`、`width`、`height`、`box_count`，`capture_batch` 为**可选**；标注文件自身摘要尚未纳入 Schema（草案第 3.3 节说明待评审）。
- 可行性规划第 3.1 节要求“图片与标注通过数据集清单中的图路径、图片 SHA-256、标注路径、标注 SHA-256 绑定”，但当前草案 Schema 缺标注摘要字段，属于需要补的口径。
- 数据检查 G0 要求“同一批次不跨划分”与批次泄漏检查（可行性规划第 6.2 节），依赖可靠的 `capture_batch`；可选字段会使该检查无法执行。
- 重命名/删除图片必须同步标注；Windows 下大小写、保留名、路径长度都需要显式处理（可行性规划第 3.1 节、R11）。

**建议选项**

采用 **Q7-A：镜像目录 + 无每图版本字段 + 标注摘要与采集批次必填**：

1. **命名与对应**：`annotations/<采集批次>/<图片主名>.json`，测试集 `test-annotations/<采集批次>/<图片主名>.json`，与图片批次目录镜像；图片扩展名替换为 `.json`。标注内 `image` 字段必须与数据集清单样本 `image` 规范化后一致（路径与内容双重校验，不靠目录遍历猜测）。
2. **唯一性与 Windows 兼容**：同一数据集内标注路径唯一；大小写不敏感比较下不得冲突；重命名/删除图片时同步处理标注，图片或标注摘要不一致时训练和测试必须拒绝。
3. **每图版本字段**：**首版不加**每图 `annotation_version`；标注格式版本由数据集清单 `2.0`（必要时由项目格式）统一声明。P2 定稿时从 `annotation.schema.json` 删除可选 `version` 字段（草案正文第 3.1 节本来就没有它），避免“Schema 有、文档没有、语义未定”的三方不一致。若评审坚持保留，必须写明“该字段不是权威版本、不得用于兼容判断”，并同步草案正文。
4. **标注摘要**：检测数据集清单 `2.0` 增加 `annotation_sha256` 并设为**必填**（与图片 `sha256` 并列），使图片与标注都被摘要绑定；校验时读取标注计算摘要并核对。
5. **采集批次**：检测数据集清单 `2.0` 的 `capture_batch` 由可选改为**必填**（至少校验器强制存在），保证批次级划分与泄漏检查可执行；旧草案例样需补字段（当前只是草案，无生产数据）。
6. **版本变化语义**：改标注内容产生新的标注摘要 → 数据集清单摘要变化 → 新训练记录引用新清单副本；旧训练记录引用的旧清单副本不变，不能被新标注“污染”。

**理由**

1. 镜像布局与现有项目 `data/` 结构一致，便于备份、检查和界面过滤。
2. 路径 + 标注内 `image` 双重校验能发现错配；`annotation_sha256` 能发现“路径不变但内容被换”的情况，补齐 G0/G1 追溯链。
3. 不加每图版本字段最简单：同一数据集内不会出现多版本标注，避免校验器做版本分派和迁移；课堂项目生命周期短，数据集级版本足够。
4. `capture_batch` 必填是批次不泄漏检查的前提，可选会让 G0 规则无法真正执行。
5. Windows 大小写/保留名/长度问题必须在格式定稿时一次说清，不能留给实现各自处理。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 每图加 `annotation_version` | 每图 JSON 带版本字符串 | 标注格式可独立演进 | 同一数据集多版本共存，校验器需版本分派与迁移；课堂短周期收益低；需同步文档/Schema | 不推荐；若保留须限定为非权威 |
| B2 扁平目录不镜像批次 | `annotations/<主名>.json` | 目录浅 | 批次重命名/冲突/训练测试隔离弱化，与项目数据布局不一致 | 不推荐 |
| B3 标注与图片同目录 | 图片旁放同名 JSON | 成对查看方便 | 图片目录混杂 JSON，与“图片按批次、标注独立目录”的草案冲突 | 不推荐 |
| B4 命名承载类别/框信息 | 文件名写类别等 | 浏览直观 | 明确禁止（可行性规划第 3.1 节），改名即改语义 | 不可接受 |
| B5 标注摘要保持可选 | 只绑定图片摘要 | 少一个字段 | 标注被替换但路径不变时无法自动发现；G0/G1 追溯不足 | 不推荐 |

**影响文件与后续工作**

- 检测数据集清单 `2.0` Schema：`annotation_sha256` 必填、`capture_batch` 必填（与 `schemas/detection/README.md` 的“待决字段”说明同步）；
- `schemas/detection/annotation.schema.json`：删除或明确 `version` 字段；
- 项目格式：标注目录约定与任务字段；
- 导入/标注界面：保存、重命名、删除同步；数据检查：路径、摘要、大小写冲突；
- 测试：路径对应、`image` 不一致拒绝、大小写冲突拒绝、重命名同步、摘要不符拒绝、批次跨划分拒绝。

**若已决定应如何记录**

- 记录中写明命名规则、是否保留每图版本字段（以及保留时的非权威说明）、`annotation_sha256` 与 `capture_batch` 的必填结论；
- 指定 P2 定稿时同步修改的段落：草案第 3.1、3.3 节、`schemas/detection/README.md` 与两个 Schema 文件；
- 若决定暂不增加标注摘要，必须记录补偿措施（例如校验时计算但不入清单），并说明对 G0/G1 追溯的影响。

### 3.8 Q8：量化容差与阈值冻结责任

**问题（契约草案原文）**：量化后允许的框偏移、IoU 下降和置信度误差是多少？由谁在何时冻结？

**背景与现状**

- 可行性规划第 6.3 节给出候选值（**全部待 P3/P6 实测后冻结**）：训练框架与 ONNX Runtime 浮点一致性可要求匹配框 IoU ≥0.99、置信度绝对差 ≤1e-3；letterbox 反算角点误差 ≤1 像素；量化前后 mAP@0.5 绝对下降 ≤0.03、各类召回下降 ≤0.05、固定样本匹配率 ≥90%（IoU ≥0.5 且类别一致）；板端实时性建议 ≥5 fps、端到端延迟 ≤200 ms；学生新样本建议 20 张中至少 75% 出现正确类别且 IoU ≥0.5。
- [模型接口与产物契约](model-contract.md) 第 8 节：验收阈值必须在运行验证前按任务、精度和设备确定并版本化，不得看到失败结果后放宽；固定样本只做交接冒烟，不能替代测试集效果评估。
- 可行性规划第 6.1、6.4 节：三类检查（训练到部署格式、转换/量化前后、教学效果）互相独立；转换成功不等于板端验证通过；失败或未执行不能标记为可用。
- 当前没有 K230/K210 工具链、没有量化转换产物、没有板端运行记录，所有数值都无实测依据。
- 责任分配在现有文档中只到“需 lead/课程负责人决定”（可研 Q7、Q11），没有写清“谁提出、谁确认、谁归档”。

**建议选项**

采用 **Q8-A：P1/P2 只定“责任、时点、流程”，数值在对应阶段运行前冻结**：

1. **不在 P1/P2 冻结任何量化/板端数值**。P1/P2 只批准责任分工、冻结时点、配置内容与失败处理规则；数值以可行性规划第 6.3 节候选值为讨论起点，不是已冻结值。
2. **冻结时点**：
   - P7 量化一致性验证**开始前**：冻结量化前后一致性阈值（框角点/IoU 下降、mAP/召回变化、固定样本匹配率、坐标容差），同时冻结校准集清单与量化方案；
   - P8 板端验收**开始前**：冻结“板端 vs 电脑参考”的比较阈值与实时性/资源阈值（帧率、延迟、内存），并绑定具体板卡/固件/运行时；
   - P9 课堂验收**开始前**：冻结学生自训模型 + 新样本的效果阈值与样本集。
3. **责任分工**（角色名可按实际组织调整，但职责必须分开）：
   - 工程负责人：提出可测口径、实现比较工具、给出候选值并解释测量方法；
   - 课程/验收负责人：确认教学可接受度并在验收配置上签字；
   - lead：批准并宣布冻结，负责归档与版本登记；
   - 硬件负责人：确认板卡、固件、转换器与运行时版本及其实测记录；
   - 实现/训练负责人不得单方面冻结自己负责通过的阈值。
4. **阈值配置与绑定**：冻结后写入版本化阈值配置，至少包含匹配算法版本、IoU/分数阈值、坐标空间、坐标/置信度容差、指标口径、测试集与固定样本摘要、产物 ID 与清单摘要、量化方案与校准集摘要、设备/固件/工具链版本；与产物 ID 和清单摘要绑定。
5. **失败处理**：未达标时产物标记失败/未验证，不得改阈值重跑；调整模型/量化/数据后作为新产物重新验证。确需修改阈值，必须作为新的验收配置重新评审并说明理由，不能覆盖或静默替换旧记录。
6. **候选值引用**：决策记录中引用可行性规划第 6.3 节候选区间时，必须标注“候选、未冻结”，不得写成“已定阈值”或“验收标准”。

**理由**

1. 没有工具链、量化和板端数据时冻结数值是无依据的；契约要求“运行前冻结”，而运行指 P7/P8/P9，不是 P1/P2。
2. 责任分离避免“自己定标准自己通过”，也避免课程可接受度被技术实现方替代表达。
3. 失败重跑规则防止“调阈值到通过”，这是契约第 8 节的硬要求。
4. 先定机制可以立即解除 P2 的阻塞；数值留到有实测的阶段，减少无效返工。

**备选与代价**

| 备选 | 做法 | 优点/适用 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| B1 P1/P2 直接冻结数值 | 现在拍板所有容差 | 开发目标明确 | 无实测依据，容易过松/过严；后续修改等于违约或产生大量再验证 | 不推荐 |
| B2 由实现/训练负责人单方决定 | 谁实现谁定阈值 | 效率高 | 标准与验收不独立，课堂可接受度未确认；易出现“技术通过但课堂不可用” | 不推荐 |
| B3 不设数值只做定性判断 | 看情况判断好坏 | 简单 | 无法判定通过/失败，不能验收；记录不可复现 | 不可接受 |
| B4 看到板端结果后调整阈值 | 先跑再定标准 | 可能减少返工 | 违反契约第 8 节，结论无效 | 明确禁止 |

**影响文件与后续工作**

- 阈值配置结构与 `validation.thresholds` 的版本绑定方式（当前只有 `path`，P2 需定义结构）；
- 验证记录、验收报告、[项目状态报告](status-report.md)与[目标机离线验收清单](acceptance-checklist.md)的口径；
- P3 实测报告的输出口径（为 P7/P8 冻结提供数据）；P7/P8/P9 的验收流程与分工；
- 测试：阈值文件缺失拒绝、阈值与产物绑定校验、超阈值判定失败、旧阈值不得复用。

**若已决定应如何记录**

- 记录中只写“责任分工 + 冻结时点 + 配置内容 + 失败处理 + 候选值来源”，明确“数值未冻结”；
- 每次真正冻结时另立一条决策记录（日期、责任人、数值、依据、影响产物与测试集），并与本次记录互相链接；
- 把“谁提议、谁确认、谁批准、谁归档”写成具体角色，不写“相关负责人”这类不可追踪的表述。

## 4. 建议的决策顺序与最小可行组合

### 4.1 决策门槛：必须先定与可延后

| 门槛 | 时点 | 必须关闭的问题 | 理由 | 未关闭的后果 |
| --- | --- | --- | --- | --- |
| 门槛 A | 进入 P2 定稿前 | Q1、Q2、Q5、Q6、Q7、Q3 | 这些决定检测契约版本线、类别下限、坐标、标注文件与后处理结构；P2 的 Schema 草案和样例校验直接依赖它们 | 无法冻结 Schema；实现方只能各自猜测，造成返工和口径分裂 |
| 门槛 B | P4 实现前 | Q4（原则可在门槛 A 随 Q3 一并确认） | 运行参数权威、派生配置与验证流程决定后端与界面行为 | 运行时可能各自使用默认参数，固定样本不可复现 |
| 门槛 C | P7 量化一致性运行前 | Q8（机制的负责人/时点可在门槛 A 先行确认） | 量化阈值要等工具链与量化产物出现后才有依据；机制不定会拖延 P7 | 验收结论不可复现或事后放宽 |
| 后置子决策 | P6 工具链结论后 | Q1 的板端版本线、Q3 的板端执行方 | 依赖 nncase/CanMV 版本、算子支持和板端运行时能力实测 | 提前承诺可能逼出错误结构，后续主版本变更成本高 |

决策依赖顺序建议：**Q1 → Q5 → Q7 → Q6 → Q2 → Q3（+Q4 原则）→ Q8 机制**。Q1 先定是因为它决定所有 Schema 的版本号和接收方支持范围；Q5/Q7/Q6 决定数据与标注格式；Q2 决定类别下限的落点；Q3/Q4 决定清单后处理结构与运行行为；Q8 最后只定机制，数值在 P7 前另立记录。

按阶段看哪些可以延后：**Q8 的数值**可在 P3 实测后校准、最迟 P7 量化验证前冻结；**Q1 的板端版本线与 Q3 的板端执行方**延后到 P6 工具链结论；**Q4 的派生配置与界面细节**延后到 P4/P5 实现前；只有门槛 A 的六项不能延后到 P2 定稿之后。

### 4.2 最小可行组合（建议打包批准）

如果 lead 希望一次批准一个可自洽的组合，建议按以下“最小可行组合”评审（**仍是建议，不是决定**）：

| 编号 | 组合中的建议 | 依赖说明 |
| --- | --- | --- |
| Q1 | 模型契约 `1.1`、数据集清单 `2.0`、项目格式 `2.0`、消息协议 `1.1`；板端 P6 后另定 | 四条版本线独立；分类 `1.0` 冻结 |
| Q2 | 检测允许 1 类，分类保持至少 2 类 | 与 Q1 的 `1.1` 条件约束一致 |
| Q3 | 后处理逐阶段声明执行方；首版模型图不含 NMS；电脑端全 `host`，板端执行方 P6/P7 再定 | 结构预留，能力后置 |
| Q4 | 参数唯一来源为清单；运行时不改；调整走派生配置 + 新 ID + 重验证 | 与 Q3 一起构成后处理规则 |
| Q5 | 标注整数、结果浮点、统一原图像素；归一化仅内部 | 标注、结果、参考结果、匹配四处一致 |
| Q6 | 允许空标注 `boxes: []`，显式、单独统计、默认提示上限 15%（非验收阈值） | 数据集清单 `box_count: 0` 可表达 |
| Q7 | 镜像标注目录；无每图版本字段；`annotation_sha256` 与 `capture_batch` 必填 | 补齐摘要与批次追溯 |
| Q8 | 机制现在定：工程提出 + 课程/验收负责人确认 + lead 冻结归档；数值 P7/P8/P9 运行前分别冻结 | 数值引用可行性规划第 6.3 节候选值，标注未冻结 |

**这个组合为什么“最小可行”**：

- 覆盖 P2 定稿所需的全部结构决策，不需要硬件、工具链或实测数据；
- 不提前承诺板端契约形态（Q1 板端部分、Q3 `device` 部分、Q8 数值后置），避免在 P6 前制造无证据约束；
- 逐阶段执行方与“首版不含 NMS”是**避免 P6 结构性返工**的关键设计，虽然增加一点 Schema 复杂度，但比 P6 再升版便宜；
- 若组合被批准，P2 可以立即起草 Schema、样例和拒绝场景测试；P4/P5 可以并行准备；P6/P7 只等工具链和板端实测结论。

**组合不成立、需要重新评审的触发条件**：

1. P3 实测发现 CPU 训练方案不可行并改变课堂流程（通常不改格式，但可能改变类别数/数据规模）；
2. P6 发现转换器或板端运行时**必须**在模型图内含 NMS，或必须改变后处理阶段归属（重开 Q3，可能影响 Q1 板端版本线）；
3. P6/P7 发现板端运行时需要改变清单现有字段含义或必填结构（重开 Q1 板端版本线，必要时升主版本）；
4. 评审决定坐标改用归一化（重开 Q5，标注/结果/参考结果/匹配全部返工）；
5. 评审决定不允许单类（重开 Q2，课堂方案改为两类采集，课时与标注量评估重做）。

### 4.3 建议的评审顺序

1. **第一次评审（结构门）**：Q1、Q5、Q7、Q6、Q2、Q3，附 Q4 的原则部分。目标是关闭门槛 A；若时间不足，按 Q1 → Q5 → Q7 优先，因为这三项不关闭，Schema 无法起草。
2. **第二次评审（运行门，P4 前）**：Q4 的派生配置流程、探索模式边界、验证状态继承规则。
3. **第三次评审（量化门，P7 前）**：Q8 的数值冻结与校准集冻结；同时把 Q1 板端版本线、Q3 板端执行方作为同一批的子决策记录。
4. 每次评审后立即按第 5 节模板登记，并更新 [检测契约扩展与标注/结果格式草案](detection-contract-draft.md) 与 [检测课可行性规划](detection-feasibility.md) 的状态，不把决定留在会议纪要里。

### 5.3 记录与状态更新规则

1. **决策不等于生效**：更新 [检测契约扩展与标注/结果格式草案](detection-contract-draft.md) 状态为“已决策，待按契约流程升版与实现”，**不是**“契约已生效”“检测已实现”。能力状态仍为“未实现、未验证”，直到 P4/P6/P7/P8 有对应证据。
2. **决策不等于文档改了就算完**：按 [模型接口与产物契约](model-contract.md) 第 9 节，文档、Schema、生产方、消费方、验证五处同步才算完成；未同步前不能在状态报告、课堂材料或验收清单中写“检测已支持”。
3. **本文状态**：任一决策登记后，把本文状态改为“已决策（部分/全部，记录见……）”，但保留“检测未实现”的事实陈述。
4. **延期处理**：延后的问题必须在登记表写“延后”与再评估条件；P2 定稿前不得带着“未决”进入 Schema 冻结。
5. **冲突处理**：若决策与现有文档冲突，以决策记录为准并在本轮同步修正文档；不得出现“文档 A 说允许、文档 B 说禁止”的并存状态。
6. **不改已发布产物**：任何决策都不允许回溯修改已发布的分类 `1.0` 产物包或已冻结的验收记录；新决策只影响新版本与新产物。
