## 1. 目标与范围

### 1.1 M3 的教学结果

学生在一台离线 Windows x64 目标机上完成一条检测课链路：

```text
采集/导入图片 → 画框标注 → 训练轻量检测模型 → 电脑测试（框、类别、置信度）
→ 导出模型产物包 → 转换/量化 → K230 板端运行 → 用未参与训练的新样本验证
```

对应的可观察教学结果（**均未实现**）：

| 环节 | 学生应能看到/做到 | 当前状态 |
| --- | --- | --- |
| 标注 | 在图片上画矩形框、选择类别、保存后能重新打开和修改；类别来自项目类别表 | 未实现（无检测画框界面、无标注格式） |
| 数据检查 | 检查标注完整性、框越界、类别覆盖、训练/验证/测试划分与批次泄漏 | 未实现（现有数据检查只覆盖分类图片） |
| 训练 | 在 CPU 上训练小规模检测模型，显示进度、耗时并可取消；训练记录可追溯 | 未实现（现有训练只训练线性分类头） |
| 电脑测试 | 单图/摄像头显示检测框、类别、置信度；在测试集上给出检测指标 | 未实现（现有预测只输出类别概率） |
| 转换 | 生成新产物 ID 的转换包，记录工具链、量化与后处理配置 | 未实现（无检测导出、无转换工具链） |
| 板端运行 | K230 摄像头输入、屏幕或串口输出、实测帧率与延迟 | 未实现（无硬件、无工具链） |
| 项目保存 | 标注、数据清单、训练记录、模型引用与转换记录随项目保存和恢复 | 未实现（现项目格式只支持分类任务） |

检测不是分类的“多类别变体”：一张图片可以有任意数量、位置和类别的框，输出是集合而非单个标签。标注、数据清单、输出语义、后处理和评估都不能复用分类的“一图一类别”假设。

### 1.3 范围

本规划覆盖 M3 的 K230 检测课。范围内：

- 单批或少量类别的图像目标检测（建议 1～3 类），轴对齐矩形框。
- Windows x64 离线、普通 CPU 电脑（无独立显卡）采集、标注、训练与电脑测试。
- K230 一路的转换、量化和板端最小闭环。
- 学生自训模型 + 未参与训练的新样本的课堂验收。

范围外（不在 M3 承诺内）：

- 实例分割、旋转框、关键点、多人姿态、目标跟踪、视频时序模型。
- K210 完整课堂流程（属 M4，需独立网络与转换链，不能假设 K230 路线直接可用）。
- M5 的声音与姿态实验；两者可复用契约扩展流程，但不占用 M3 验收。
- 多板卡并行、云训练、自动调参、从零训练大型网络。

### 1.4 启动条件

M3 检测课进入硬件阶段前，以下条件缺一不可；未满足时只能做无硬件前置工作（见第 7 节），板端结论保持“未验证”：

1. 契约扩展方案获批（任务、输出语义、后处理、执行方、板端字段与版本策略，见第 2 节）。
2. 检测数据与标注格式定稿，并能在现有项目 `data/` 结构内校验和追溯（见第 3 节）。
3. 训练可行性实测完成：至少一个候选模型能在可接受时间内完成小数据微调并导出 ONNX（见第 4 节）。
4. 指定 K230 板卡型号、摄像头、屏幕/调试线，以及固定的 CanMV/K230 SDK 与 nncase 版本组合（见第 5 节）。
5. 转换工具链可在**离线**环境安装和运行，或明确记录为阻塞并评估教师机方案。
6. 验收阈值在运行前冻结并版本化（见第 6 节）。

## 2. 与现有分类契约的差异

本节只给出**待扩展清单**，不修改 [模型接口与产物契约](model-contract.md)。任何扩展都必须按契约第 9 节同步文档、JSON Schema、生产方、消费方和验证，并在实现前评审；现有分类 `1.0` 产物包的字段与语义保持不变。

契约中的强制规则对检测同样适用，不因任务类型改变：

- **完整产物包**：仍以 `manifest.json` 为唯一入口，权重、标签、固定样本、参考结果和阈值作为整体交付；不单独交付缺少元信息的权重文件，模型、标签与处理配置整体加载和切换（契约第 2、3 节）。
- **SHA-256 与产物 ID**：包内文件摘要用于检查完整性和文件对应关系；每次训练或转换生成新的 `artifact_id`；已发布包不可原地修改；失败或取消的临时产物不得加载（契约第 2、5 节）。
- **交接校验**：训练发布、电脑加载、模型转换、板卡部署四个交接点都要执行适用校验；转换成功不等于板端验证通过；没有实物测试时板端状态必须保留为未验证（契约第 5 节）。
- **兼容升级**：改变字段含义、必填结构或处理语义升主版本，兼容的可选扩展升次版本；接收方声明支持范围，未知主版本拒绝，不自动猜测或隐式迁移旧模型（契约第 7 节）。
- **固定样本与验收**：固定样本只做交接冒烟，代表性测试集用于效果评估；阈值在运行前按任务、精度和设备冻结，不得事后放宽（契约第 8 节）。

### 2.1 差异总览

| 维度 | 分类契约 `1.0`（已实现） | 检测需求（规划） | 影响 |
| --- | --- | --- | --- |
| 任务类型 | `image_classification` | `object_detection`（Schema 枚举已预留，校验器未支持） | 校验器、训练、导出、运行时、界面都要分任务实现 |
| 输出含义 | `class_logits` / `class_probabilities`，类别轴 | `raw_detections` 或 `detections`（枚举已预留，语义未定义） | 须定义检测头布局、解码参数、框格式与坐标单位 |
| 输出数量 | 单分类输出 | 原始头可能多输出，也可能单输出 | Schema 允许最多 8 个输出，但校验器只处理分类语义 |
| 后处理 | `softmax`，仅 `host` | 解码 + NMS/框映射；`host` 或 `device`，按阶段声明执行方 | 需新增步骤类型、参数与“只执行一次”校验 |
| 输入预处理 | `resize(stretch)` 等；运行时拒绝 `letterbox` | 检测通常需要等比补边（letterbox）并反算框 | 预处理、运行时要支持 letterbox 及其坐标映射 |
| 标签 | `labels.json` 有序类别名数组 | 类别表语义可沿用，但每张图片另有框标注；可能只有 1 类 | 单类支持与最小类别数需决策；背景类不得混入标签 |
| 固定样本 | 输入张量摘要 + 原始输出/预测类别 | 输入张量摘要 + 最终检测结果（框/类别/置信度）+ 匹配规则 | 需新的参考结果结构与比较算法，见 2.4 |
| 数据清单 | `1.0`：每样本一个类别 | 每图多个框、无单一类别；需标注文件引用与摘要 | 建议数据集清单升主版本（样本必填结构变化） |
| 项目格式 | `task` 只允许分类 | 检测项目需要任务类型、标注与检测模型引用 | 项目格式版本需升级 |
| 电脑运行时 | 分类预测/评估 | 检测结果渲染、检测评估（IoU 匹配、mAP） | 运行时与界面都要扩展 |
| 板端/运行时 | 仅 `onnxruntime` + CPU 主机 | K230 nncase/CanMV、kmodel、固件范围 | Schema 已预留板端字段，但校验器显式拒绝；需新增运行时与模型格式 |
| 转换 | 无量化转换 | 转换器版本、校准数据、量化方案、后处理位置 | 现有 `conversion` 字段偏通用，检测与板端特定项不足 |
| 消息协议 | 预测载荷含类别 ID/概率 | 检测载荷含框、类别、置信度与阈值 | 协议次版本扩展，保持旧消息可读 |
| 评估指标 | 准确率、各类召回、混淆矩阵 | 检测需 IoU 匹配、mAP、各类 AP/召回 | 指标定义、阈值和样本集必须显式版本化 |

### 2.2 输入、输出 schema 与结果结构（草案）

检测产物清单必须回答契约第 4.2 节的强制问题；当前 Schema 只能表达少量占位字段，以下为**待评审草案**，字段名不是最终契约，也不构成可加载清单：

```text
task: object_detection
inputs:
  - 图像张量：名称、形状（固定批次 1）、dtype（float32 或量化后的 uint8/int8）、
    布局（NCHW/NHWC）、颜色（RGB/BGR）、像素范围；动态维度须声明范围且目标运行时支持
outputs:
  - 语义：raw_detections（原始检测头）或 detections（已解码结果），必须唯一明确
  - 若为 raw_detections：记录输出数量、每层形状、解码所需参数
    （anchor-free 的中心先验/步长，或 anchor-based 的 anchor 表引用）
  - 若为 detections：记录每行元素顺序、框格式、坐标空间、类别与置信度字段位置
postprocessing:
  - 每一步声明执行方（host 或 device）与有序参数：
    decode_detections：box_format（xyxy / cxcywh）、box_space（model_input / resized / source）、
      strides/anchors、score_mode（objectness_x_class / class_probability / sigmoid 等）
    nms：algorithm（greedy 等）、iou_threshold、score_threshold、class_agnostic、
      max_detections、是否按类别分别执行
    map_boxes_to_source：letterbox/scale 参数、补边位置、取整规则
  - 明确 NMS 是否在模型图中；图内执行时外部不得重复执行
preprocessing:
  - letterbox 的缩放方式、插值、补边颜色/位置、取整规则，以及反算框所需参数
quantization:
  - 实际输入输出 dtype、scale、zero point、逐通道量化轴；
    不得假定量化模型仍使用浮点输入输出
labels:
  - labels.json 有序类别名；数组下标即 class_id；背景类不写入标签；
    若模型含背景/忽略类，必须在清单中显式声明映射
```

第一版建议**模型图不含 NMS、不绑定原图坐标**：模型输出原始检测头，解码与 NMS 由清单声明的 `host`（电脑测试）或 `device`（板端）执行。这样模型可同时用于电脑和板端，转换前后差异更容易定位；代价是两端都要按同一组清单参数实现后处理，必须用固定样本证明一致。写进产物包的是参数，不是两端各自的“默认值”。

电脑测试与消息协议中的检测结果建议采用如下结构（草案，坐标以**原图像素**为单位）：

```json
{
  "artifact_id": "art-20261119-0001",
  "image": "test-images/batch-1/001.png",
  "detections": [
    {
      "class_id": 0,
      "class_name": "水杯",
      "score": 0.93,
      "box": { "x1": 120, "y1": 80, "x2": 320, "y2": 340 }
    }
  ],
  "thresholds": { "score": 0.25, "iou": 0.45, "max_detections": 100 }
}
```

- 结果按 `score` 降序，最多 `max_detections` 条；无检测时 `detections` 为空数组。
- `class_id` 只能是 `labels.json` 的有效下标；`class_name` 是显示用冗余字段，不得用于映射。
- 框必须使用约定格式和单位；不能一部分用输入坐标、一部分用原图坐标。
- 该结构是电脑端/消息层结果，不是模型输出张量；模型张量语义仍由清单声明。

### 2.3 后处理位置

分类契约只允许 `host` 执行 `softmax`。检测必须把“解码 → NMS → 框映射”拆为有序阶段，逐段声明执行方：

| 阶段 | 电脑测试 | 板端运行 | 必须记录 |
| --- | --- | --- | --- |
| 预处理（letterbox 等） | `host` 或电脑程序 | 板端程序 | 缩放、补边、取整与反算参数 |
| 模型推理 | ONNX Runtime | K230 运行时 | 输入输出张量、量化参数 |
| 解码 | `host`（推荐首版） | `device` | 步长/anchor、框格式、置信度公式、坐标空间 |
| NMS | `host`（推荐首版） | `device` | 算法、IoU/分数阈值、类别处理、最大数量 |
| 映射回原图 | `host` | `device` | letterbox 比例、补边偏移、取整 |
| 结果输出 | 界面/协议 | 屏幕/串口 | 结果字段与排序 |

约束：

- 同一个操作只能由约定的一方执行一次；模型图已含 NMS 时，外部不得再次执行。
- 电脑端与板端可以使用不同执行方，但必须使用清单中**同一组参数**；参数变化产生新的派生配置/产物，不得静默改阈值。
- 板端若因算力裁剪候选数或最大检测数，必须记录为不同配置并重新验证，不能当作同一次验证通过。
- 任何一端缺阶段、重复阶段或使用默认参数，固定样本一致性校验应失败。

### 2.4 标签格式与固定样本校验

**标签**：`labels.json` 继续使用 UTF-8 有序字符串数组，下标即类别 ID，顺序不得在加载时排序或重编号；检测的类别表沿用这一语义。与分类的差别在**每图标注**：标注使用 `class_id` 整数，不写类别名（见第 3 节）。单类检测是否允许触及当前 Schema 的“至少 2 类”下限，需要单独决策（见 8.2 Q3）。

**固定样本**：分类固定样本验证输入张量摘要、原始输出和预测类别；检测固定样本必须验证“最终检测集合”的一致性。建议参考结果结构（草案）：

```json
{
  "sample": "validation/sample-01.png",
  "input_tensor_sha256": "（预处理后输入张量摘要）",
  "detections": [
    {
      "class_id": 0,
      "score": 0.93,
      "box": { "x1": 120, "y1": 80, "x2": 320, "y2": 340 }
    }
  ]
}
```

- 参考结果由电脑端运行时按产物包参数生成，不是人工画的标注；人工标注只用于代表性测试集效果评估。
- 比较采用**顺序无关的匹配**：按分数降序、同类、IoU 贪心匹配；分别统计匹配框的坐标/分数误差以及遗漏和多余框。
- 匹配算法版本、IoU 阈值、分数阈值和坐标容差写入 `thresholds.json` 与验收配置，随产物保存；不得在失败后临时放宽。
- 固定样本至少覆盖：单目标、多目标、目标贴边、无目标（可选）；少量样本只做交接冒烟，不能代替测试集效果评估（契约第 8 节）。

### 2.5 待扩展清单（只列项，不改现有契约文档）

| 编号 | 领域 | 现状 | 待扩展内容 | 不扩展的后果 |
| --- | --- | --- | --- | --- |
| C1 | 任务 | 校验器只接受 `image_classification` | 支持 `object_detection`，并给出任务专属必填语义 | 检测包无法通过校验，只能停留在规划 |
| C2 | 执行方 | 只接受 `host` | 明确 `device`/`model` 的适用阶段与约束，逐阶段声明 | 板端后处理无法合法表达 |
| C3 | 输出语义 | 只处理分类 logits/概率 | 定义 `raw_detections`/`detections` 的布局、框格式、坐标空间、置信度与类别轴 | 无法判断输出如何解释，存在静默错位风险 |
| C4 | 后处理步骤 | Schema 只有 `softmax` | 增加检测解码、NMS、框映射等步骤及参数；校验“图内/图外只执行一次” | 电脑端与板端行为不可复现 |
| C5 | 预处理 | Schema 有 `letterbox` 字段，运行时拒绝 | 运行时实现 letterbox 及坐标反算；声明取整规则 | 检测框位置整体偏移 |
| C6 | 标签与类别 | 标签数量与类别数按分类约束 | 明确单类检测、背景/忽略类映射；决定最小类别数 | 课堂 1 类检测被 Schema 拒绝或被迫塞入假类别 |
| C7 | 固定样本 | 参考结果为分类概率 | 新增检测参考结果与匹配规则、阈值配置 | 无法执行契约要求的固定样本一致性检查 |
| C8 | 运行时与板端 | 仅 `onnxruntime` + 主机 CPU；板端显式拒绝 | 增加 K230/K210 运行时、固件范围、能力与模型格式（如 kmodel） | 板端产物不能合法登记，也不能被加载 |
| C9 | 转换 | `conversion` 只有转换器名/版本与通用量化字段 | 增加工具链版本、配置摘要、校准集清单、量化方式、输入 dtype、后处理位置 | 无法追溯“哪个工具、哪组参数、哪种量化”生成了板端产物 |
| C10 | 数据与训练追溯 | 训练产物记录分类数据摘要 | 检测训练记录引用标注摘要、类别表和固定样本；数据集清单新版本 | 修改标注后旧训练记录失去含义 |
| C11 | 消息协议 | 预测载荷只有类别 ID/概率 | 检测结果载荷、阈值和结果字段；协议次版本扩展 | 界面与后端无法交换检测结果 |
| C12 | 项目格式 | `task` 只允许分类，无标注引用 | 检测任务类型、标注路径/摘要、检测模型引用；格式版本升级 | 检测项目无法保存/恢复，或与分类项目混淆 |

扩展边界提示：C1～C12 中的字段名、必填性和版本在 P1 评审前不冻结；尤其不要先把检测字段塞进分类清单再“顺手”放开校验器，否则会造成同一版本号下语义不一致。

### 2.6 版本兼容策略

按契约第 7 节：改变字段含义、必填结构或处理语义时升主版本；兼容的可选扩展升次版本；接收方必须声明支持范围，未知主版本拒绝，较新次版本仅在兼容策略明确允许且能力受支持时接受；不自动猜测或隐式迁移旧模型。

建议策略（**待 lead 决策**）：

1. **分类 `1.0` 保持冻结**：现有分类字段、语义和校验行为不改；新版本接收方可读 `1.0` 分类包，旧接收方继续只接受 `1.0`。
2. **检测电脑端扩展用次版本**（例如契约 `1.1`）：新增检测专属输出语义、后处理步骤、固定样本结构、数据集清单 `2.0`、项目格式与消息协议各自升版；这些都是新增能力，不改变分类包的语义。接收方声明“支持 `1.0` 与 `1.1`”，未声明 `1.1` 的接收方按版本拒绝，不尝试解析检测字段。
3. **板端扩展单独定版**：kmodel 格式、板端运行时、执行方 `device` 若只是新增枚举和可选字段，可继续次版本（如 `1.2`）；若必须改变现有字段含义、必填结构或“主机端加载”语义，则升主版本 `2.0`，并在过渡期显式双读、禁止自动迁移。板端定版应在 P6 工具链结论之后，不提前承诺。
4. **每个训练/转换产物使用新 `artifact_id`**，转换产物记录来源产物 ID 与来源清单 SHA-256；已发布产物不可原地修改；固定样本、阈值、转换记录和板端验证记录分别保存并绑定产物 ID 与清单摘要。
5. **兼容验证必须包含拒绝场景**：分类 `1.0` 包在新接收方仍通过；检测包被旧接收方按版本/任务拒绝；未知执行方、未知后处理步骤、未知模型格式和标签错位被拒绝；不能只测“新功能能跑”。
6. **数据集清单、项目格式、消息协议与契约版本独立维护**，分别记录升级原因和接收方支持范围；不得用一个版本号同时掩盖四种格式的变化。

## 3. 数据与标注

### 3.1 建议的离线标注格式

采用**每图一个 JSON 文件**，与图片分开保存（不把框信息写进图片文件名或目录名），编码 UTF-8、无 BOM，保存时“写临时文件 → 整体替换”。最小规范示例：

```json
{
  "annotation_version": "1.0",
  "image_width": 1280,
  "image_height": 720,
  "boxes": [
    { "class_id": 0, "x": 120, "y": 80, "w": 200, "h": 260 }
  ]
}
```

- 无目标图片必须显式写 `"boxes": []`，不能缺文件或省略字段；空标注样本可作为负样本，但比例受限并单独统计。
- 标注中**只存 `class_id` 整数**，类别名、类别顺序只存在于项目 `classes` 表；修改类别名不改变 ID，调整类别顺序必须视为不兼容变更。
- `annotation_version` 独立于模型契约版本；后续字段变化需要升版并提供显式迁移，不静默解释旧字段。
- 不允许绝对路径、盘符、反斜杠和 `..`；标注文件与图片的对应关系由数据清单记录，不靠目录遍历猜测。

**坐标约定**：

| 规则 | 约定 |
| --- | --- |
| 原点 | 图片左上角 `(0, 0)`；x 向右、y 向下 |
| `x`、`y` | 框左上角坐标，单位：原图像素（导入并转 PNG 后的实际解码尺寸） |
| `w`、`h` | 框宽、高，正整数；右边界与下边界**不包含**，即 `x + w <= image_width`、`y + h <= image_height` |
| 取整 | 标注界面按整数像素取整，取整规则固定并写入文档；不得静默 clamp 越界框 |
| 最小尺寸 | 建议 `w >= 2` 且 `h >= 2` 像素；过小框应放大或剔除并说明原因 |
| 合法性 | `x >= 0`、`y >= 0`、`w > 0`、`h > 0` 且完全在图像内；越界、零面积、负值、NaN/Inf 一律拒绝 |
| 重复框 | 同类框 IoU 大于约 0.95 视为疑似重复，数据检查报出并要求人工确认，不自动删除 |
| 重叠 | 不同类别的重叠框合法；同类遮挡/重叠是正常样本，不按重复处理 |
| 不支持 | 多边形、旋转框、关键点、掩码、框属性/难度标签不进入首版格式；遇到未知字段按 Schema 拒绝，避免拼写错误被忽略 |

图片导入时继续沿用现有“转 RGB PNG、按内容 SHA-256 去重”的做法；标注与图片通过数据清单中的图路径、图片 SHA-256、标注路径、标注 SHA-256 绑定。导入或人工修改后，旧训练记录引用的清单副本不变；若标注内容变化而路径不变，新的清单摘要必须变化，旧运行不得被新标注“污染”。

标注编辑约束：

- 保存采用原子替换；取消或失败不留下半写标注。
- 重命名图片时同步重命名对应标注；删除图片时同步处理标注；两者摘要不匹配时训练和测试必须拒绝，不能继续。
- 标注只描述“看到什么”，不写模型预测结果；不接受把预测框回灌成标注而不经人工确认。

### 3.2 每类最小样本与批次组织

检测比分类需要更多“实例”，以下均为**建议值，未冻结**；P3 实测课堂时间和训练耗时后再定稿，正式验收阈值必须在运行前冻结：

| 指标 | 开发最小（只验证格式/流程） | 首课建议 | 严格验收建议（待冻结） |
| --- | --- | --- | --- |
| 类别数 | 1 | 1～2 | 1～3 |
| 每类标注实例数（训练+验证） | ≥ 20 | ≥ 60 | ≥ 100 |
| 含该类目标的图片数 | ≥ 15 | ≥ 40 | ≥ 60 |
| 每类采集批次数 | ≥ 2 | ≥ 4 | ≥ 5 |
| 每类验证图片数（需有该类目标） | ≥ 5 | ≥ 10 | ≥ 15 |
| 每类独立测试图片数 | ≥ 8 | ≥ 12 | ≥ 20（另采，未参与训练/调参） |
| 无目标负样本占训练图片 | 0～10% | 0～15%，记录比例 | 记录比例并按需覆盖误检场景 |
| 最大图片数（课堂建议） | 100 | 300 | 500（待实测） |

批次组织与划分：

- **采集批次**沿用分类定义：同一次采集场景/时间的一组图片为一个批次，批次名使用字母、数字、`.`、`_`、`-`，长度 1～64。
- 训练/验证按**图片和批次**划分，不按框划分：同一批次只能出现在一个划分；同一图片的所有框随图片整体进入同一划分。
- 验证集必须覆盖所有类别且最好来自不同批次；测试集独立采集、冻结后不参与训练、调参或阈值选择。若根据测试结果修改方案，另设新的最终测试集。
- 每类至少要出现在 2 个批次中，否则无法做批次级划分，数据检查应拒绝并要求补采。
- 固定样本从现有数据中挑选 2～4 张（建议含单目标、多目标、贴边），只用于交接冒烟，必须单独记录、不混入测试集指标。
- 课堂采集指导：换背景、距离、光照、角度；避免同一场景连拍大量几乎相同图片；目标和框要清晰可辨；教师抽查标注质量（如随机抽 10% 复核框是否紧贴、有无漏标/多标）。

标注工作量要计入课堂预算：按每张 1～3 个框、每个框数秒估算，60～100 张图片的标注可能占用可观课时。是否需要课前预标注、教师示范或精简数据规模，属于开放问题（见 8.2 Q4/Q5）。

### 3.3 与现有项目 `data/` 结构的兼容方式

分类项目现有布局（[数据与运行基线](data-and-runtime-baseline.md) 第 2 节）保持不变：

```text
学生项目/
  project.json
  data/
    dataset-manifest.json
    images/<类别>/<采集批次>/<图片>
    test-images/<类别>/<采集批次>/<图片>
```

检测项目建议在同一项目根结构下使用镜像布局（**建议草案，未实现**）：

```text
学生项目/                              # project.json 中 task = object_detection
  project.json
  data/
    dataset-manifest.json              # 建议数据集清单 2.0（任务、标注引用）
    images/<采集批次>/<图片>.png        # 检测图片不再按类别分目录
    annotations/<采集批次>/<图片>.json  # 与图片同名（扩展名 .json）的标注
    test-images/<采集批次>/<图片>.png
    test-annotations/<采集批次>/<图片>.json
  runs/<训练记录 ID>/                  # 复用现有布局
  exports/<产物 ID>/                  # model-package/ 与 conversion-record.json，复用现有布局
  validation-runs/                    # 绑定产物摘要的验证记录，复用现有布局
  logs/
```

采用“图片与标注分目录、按批次镜像”的理由：

- `data/annotations/` 已在总体路线第 5 节的项目布局中预留，属于项目数据的自然组成；不把大量 JSON 混入图片目录，便于备份、检查和界面过滤。
- 图片目录用批次组织而不是类别目录组织：一张图可含多类多个目标，用类别目录会强行把图片归类，和检测语义冲突。
- 训练/验证划分由清单中的 `split` 决定，不从目录名推断；测试集仍在 `test-images/` 下，与分类项目的隔离方式一致。
- 图片、标注、清单都使用相对路径；复制项目目录到另一台电脑后仍能打开（可移植性要求与现有项目一致）。

建议的数据集清单 `2.0` 草案（示意，字段名与版本待 P2 评审，不是已实现 Schema）：

```json
{
  "dataset_version": "2.0",
  "dataset_id": "ds-20261119-0001",
  "task": "object_detection",
  "created_at": "2026-11-19T10:00:00+08:00",
  "classes": ["水杯", "书本"],
  "samples": [
    {
      "path": "images/batch-1/001.png",
      "sha256": "…64 位小写十六进制…",
      "capture_batch": "batch-1",
      "split": "train",
      "width": 1280,
      "height": 720,
      "annotation_path": "annotations/batch-1/001.json",
      "annotation_sha256": "…64 位小写十六进制…",
      "box_count": 2
    }
  ]
}
```

兼容规则：

| 类别 | 内容 |
| --- | --- |
| 复用 | 项目根目录与 `project.json`；`data/`、`runs/`、`exports/`、`validation-runs/`、`logs/` 的角色；批次命名规则；`classes` 有序表与类别 ID 语义；产物包、SHA-256、产物 ID、固定样本、校验器规则；相对路径与原子保存要求 |
| 新增 | `project.json` 的检测任务与标注引用；`data/annotations/`、`test-annotations/`；数据集清单 `2.0` 与标注校验；检测导入、标注界面、检测训练/测试入口；转换记录中的检测与板端字段 |
| 禁止 | 在 `labels.json` 之外另用文件名/目录名承载类别；把分类 `1.0` 数据清单改义来存框；同一个项目混用分类与检测清单；自动把分类项目“升级”为检测项目；复用旧产物 ID 或旧训练记录冒充检测产物 |

旧分类项目不受影响；检测项目在只支持分类的旧程序中被打开时，必须按任务/格式版本明确拒绝，而不是忽略标注或猜测任务。不存在自动迁移：若要把分类项目的图片复用到检测课，应新建检测项目并重新标注、重新训练，保留来源关系说明。

## 4. 训练与导出（Windows CPU 离线）

### 4.1 约束与原则

- 目标环境为 Windows x64、离线、普通 CPU；不依赖网络下载预训练权重、Python 包或运行时。权重和依赖必须随离线包或在离线教师机上准备，记录来源、版本、SHA-256 与许可证（沿用 [数据与运行基线](data-and-runtime-baseline.md) 第 9 节的记录方式）。
- 训练、导出、测试都在电脑上完成；板端只运行转换后的模型。
- **以板端可转换性反推模型**，而不是训练完再尝试转换：先确定板卡/固件/转换器版本与支持算子，再筛选模型结构和输入配置；转换不可行时提前更换模型，不把失败留到课堂末尾。
- 电脑端先完成“训练框架 → ONNX → ONNX Runtime”的一致性验证，再进入转换；转换成功不能替代板端验证。

反推顺序建议：

1. 固定板卡型号、固件、nncase/CanMV 版本、摄像头分辨率和板端内存上限。
2. 收集该组合的算子限制、输入尺寸限制和已知可运行示例；没有证据的结构不进入候选。
3. 列候选检测网络的 ONNX 算子清单，排除动态形状、难以转换的算子、图内 NMS 等风险项。
4. 用小数据先跑通“训练 → 导出 → 转换”链路，再扩大训练数据；不能先用大模型训练再回头裁剪。
5. 记录“模型结构 + 输入尺寸 + 量化方案 + 后处理位置”作为一组不可拆分的兼容组合。

### 4.2 候选轻量检测模型（待验证，不作承诺）

| 候选 | 类型/输出 | 优点 | 主要风险 | 取舍要点 |
| --- | --- | --- | --- | --- |
| YOLO 系列小模型（如 YOLOv8n、YOLO11n 一类） | anchor-free，多尺度原始头，NMS 在模型外 | 结构小、导出 ONNX 资料多、PC 训练生态成熟 | 许可证（Ultralytics 系列为 AGPL-3.0，需确认离线分发与课堂使用条件）；多尺度输出与后处理参数较多；nncase 对具体结构的算子支持未验证 | 若许可证可接受且 P3 实测可行，作为首候选；必须用固定小输入尺寸先验证转换 |
| YOLOX-Nano/Tiny 一类 | anchor-free，解耦头 | Apache-2.0，结构较规整，NMS 外置 | 训练/导出资料少于 YOLOv8；后处理需要按版本核对 | 许可证压力小，作为替代候选评估 |
| NanoDet-Plus 一类 | anchor-free，轻量 | 模型很小，适合低算力 | 特定损失/分布编码算子可能带来转换风险；生态资料较少 | 只有在算子清单核对通过后考虑 |
| SSDLite + MobileNetV3 检测头 | anchor-based，单阶段 | torchvision 内置（BSD-3-Clause），与现有 MobileNetV3 依赖同源；CPU 友好 | 精度通常低于同尺寸 YOLO；anchor 解码与 NMS 参数较多；对 nncase 的支持未验证 | 若许可证或转换链限制 YOLO 路线，作为保守替代 |
| EfficientDet-Lite 一类 | 轻量单阶段 | 面向移动端，资源小 | 常见导出链是 TFLite，转 ONNX/板端链路间接，风险高 | 首版不作为主候选 |

选择时必须同时评估：许可证与离线再分发、Python 依赖体积、CPU 训练时间、ONNX 导出稳定性、目标转换器算子风险、输入尺寸下的精度、后处理复杂度、是否有该板卡的公开可复现示例。**同系列任意模型不自动受支持**；路线图中的 YOLO→K230 仅是适配起点（见 [K230 板端可行性准备](k230-feasibility.md) 与路线图第 7 节）。

P3 至少并行比较两个候选（例如 YOLO 小模型与 SSDLite-MobileNetV3），用同一小数据集、同一输入尺寸、同一 CPU 记录每轮耗时、导出结果和转换筛查结论，再决定唯一原型路线；不承诺“YOLO 一定能转”或“某个候选一定够快”。

### 4.3 训练与导出流程（规划）

- **训练方式**：从本地预训练权重初始化（小数据微调），优先冻结主干、先训练检测头；是否解冻部分层由 P3 实测决定。不把从零训练深层检测网络作为课堂前提。
- **数据读取**：只使用 `train`/`val`；`test` 不参与训练、调参或阈值选择。评估指标与测试集在训练前冻结。
- **可复现性**：随机种子、线程数、批次大小、学习率、输入尺寸、依赖版本和权重摘要写入训练配置；相同配置重跑应有可解释的结果一致性。
- **指标**：mAP@0.5、各类别 AP/召回、按 IoU 匹配后的混淆/误检统计；固定样本指标与测试集指标分开报告。检测指标定义（匹配算法、IoU 阈值、分数阈值）必须版本化，不能把分类准确率直接套到检测上。
- **训练产物**：`runs/<run_id>/` 先写临时目录、成功后整体发布；记录 `config.json`、数据清单副本（含标注摘要）、`metrics.json`、权重、`training-artifact.json`（检测版格式，待定义）与来源信息。失败或取消不发布、不登记为可用。
- **导出**：固定批次 1、固定输入尺寸与 opset；`onnx.checker` 后重新读取真实张量签名；用 ONNX Runtime 在固定样本上推理并与训练框架输出比较；生成扩展后的检测 `manifest.json`、标签、固定样本、参考结果与阈值；通过校验器后才整体发布，分配新的 `artifact_id`。
- **电脑测试**：运行时只凭产物包加载，标签、预处理、后处理参数全部来自清单；首次在某个运行环境加载时执行固定样本验证；新进程加载、参数不硬编码、失败产物不出现为可用模型。
- **导出与转换是两次发布**：训练格式、ONNX 格式、转换/量化格式分别使用独立产物 ID 并保留来源关系；不能拿训练记录直接冒充可部署包。

### 4.4 训练耗时风险与教师机/跨课时方案

分类训练之所以快，是因为分类头只在一个已缓存的特征向量上训练。检测训练需要对每张图片做多次主干前向/反向和多尺度检测头计算，CPU 上可能比分类训练慢几个数量级。**当前没有任何检测训练耗时实测，不能承诺一节课内完成**（模型/导出侧的前置探测见第 4.5 节；该探测不含训练，不能替代本题）。

P3 必须先回答：

1. 在最低目标电脑或开发机上，一个候选模型、固定输入尺寸、固定数据规模，每轮训练需要多久？
2. 训练到可接受效果需要多少轮/总时间？内存峰值和模型包体积多少？
3. 导出 ONNX 与电脑端单图推理耗时多少？

按实测结果选择课堂方案（优先级待课堂负责人确认）：

| 方案 | 适用条件 | 代价/风险 |
| --- | --- | --- |
| 课堂内完整训练 | 实测总时间明显小于课堂预算（例如不超过 10～15 分钟，待定） | 依赖模型、输入尺寸和样本量足够小；效果可能受限 |
| 教师机离线预训练 + 学生微调/验证 | 课堂时间不足以从初始权重训练 | 需要教师机与数据分发流程；学生模型可追溯性、课堂主导性要说明清楚 |
| 跨课时：第 1 课时采集与标注，第 2 课时训练与电脑测试，第 3 课时转换与板端 | 训练或硬件时间超出单课时 | 需要训练记录/模型包跨课时保存与恢复；教师需管理队列 |
| 教师课后离线转换 + 下节课板端验证 | 转换工具链无法在每台学生机运行或耗时较长 | 转换等待在两节课之间；必须记录来源与哈希，不能跳过固定样本校验 |
| 预训练演示模型 + 学生数据评测 | 只作为硬件体验或故障降级 | **不能替代**路线图要求的“学生自训模型 + 新样本”验收；演示模型成功不证明学生模型可用 |

无论采用哪种方案，训练产物、数据清单、权重摘要、随机种子、环境和耗时都要记录；跨课时恢复要重新校验文件摘要与版本，迟到或旧的训练结果不得覆盖当前模型。教师机方案还须满足离线、可移植、相对路径和产物包完整性要求，不能引入开发机绝对路径或联网依赖。

### 5.1 需要记录的组合信息

路线图第 7 节要求每个板端支持组合都记录具体信息；检测课在此基础上增加检测/量化相关字段。**任何一项缺失，产物不能标记为板端可用或验证通过**：

| 转换器 | nncase（或实际工具）名称、版本/提交、宿主系统、Python 版本、转换配置 SHA-256 | 转换配置随转换记录保存 |

| 输出/后处理 | 输出语义、框格式、坐标空间、解码参数、NMS 算法与阈值、类别处理、最大检测数、执行方 | 模型图是否含 NMS 必须明确 |
| 量化 | 是否量化、static/dynamic、uint8/int8、校准清单 ID 与 SHA-256、校准样本数与来源、逐张量/逐通道、scale/zero point/轴 | 量化输入输出类型必须与实际一致 |

| 产物 | 转换产物 ID、清单 SHA-256、模型文件（kmodel 等）SHA-256、转换记录 ID/摘要 | 转换产生新产物 ID，不覆盖源包 |
| 验证 | 固定样本结果摘要、阈值配置版本、板端验证记录 ID、耗时与内存峰值 | 转换成功与板端通过分别记录 |

按以下顺序逐项留证，任一项失败即记录为阻塞并停止下游步骤：

| 编号 | 门槛 | 通过条件 |
| --- | --- | --- |
| T1 | 获取与版本固定 | 指定的板卡、固件、转换器、运行时安装包/轮子全部本地可得；记录来源、版本、SHA-256、许可证与离线安装步骤 |

### 5.3 量化

- 首版建议使用**静态量化**（uint8 或 int8，按工具支持选择），校准集从训练数据中冻结选取，不使用测试集和固定样本；建议 50～200 张、覆盖课堂光照/背景/目标大小，记录校准清单 ID、样本路径、SHA-256、数量和选取规则。
- 量化方案、校准数据摘要和转换器参数写入转换记录；转换后读回真实的输入输出 dtype/scale/zero point，不能假设仍是 float32。
- 量化前后比较必须在 PC 侧尽可能完成（转换器仿真或等价运行时）；没有仿真能力时，只能在板端完成比较，但板端结论仍不能由 PC 转换结果代替。
- 检测框回归通常比分类概率更敏感。若量化后精度不达标，可评估混合精度、保留部分浮点输出或更换量化策略；这些都是新配置/新产物，必须重新验证并更新说明，不能把“还能出框”当作通过。
- 当前契约校验器已有量化元数据字段，但电脑运行时**尚未实现量化输入输出**；这不是“量化已支持”，只是 Schema 占位。

## 6. 验收门槛

### 6.1 原则

1. **三类检查互相独立**：训练到部署格式的一致性、转换/量化前后一致性、教学效果（学生模型 + 新样本）。任何一类通过都不能替代其他类。
2. **固定样本用于交接冒烟**，代表性冻结测试集用于效果评估；两者不得混为一个指标。
3. **阈值先冻结再运行**：按任务、精度、设备在验收前确定并版本化，不得看到失败结果后临时放宽；阈值变化视为新配置，需重新验证。
4. **失败产物不可用**：任何适用门槛失败、跳过或未执行，产物不能标记为可用；转换成功不等于板端验证通过；电脑/仿真结论不等于实物板端结论。
5. **证据可追溯**：每次记录产物 ID、清单 SHA-256、运行时、设备、固件、样本集、阈值配置、时间和实际结果；通过、失败、跳过、未执行分开报告。
6. **目标机与板端不可替代**：Linux/开发机、ONNX Runtime、转换器仿真都不能替代目标 Windows 机器的课堂性能验收，也不能替代实物 K230 板端验证。

### 6.3 一致性比较与建议阈值

固定样本与量化比较的统一规则（草案）：

- 结果匹配：按分数降序、同类、IoU 贪心匹配；未匹配的参考框计为遗漏，未匹配的检测计为多余；类别必须一致。
- 坐标比较在**原图像素空间**进行；若训练/运行时使用 letterbox，必须按清单参数反算后再比较，不能直接比模型输入坐标。
- 固定样本至少覆盖单目标、多目标、贴边目标；无目标场景在测试集或单独负样本中评估。只比较固定样本不能证明泛化效果。

建议默认阈值（**全部待 P3/P6 实测后冻结，不得在看到结果后放宽**）：

| 检查 | 建议默认 | 说明 |
| --- | --- | --- |
| 预处理输入张量 | SHA-256 完全一致 | 用于定位解码、颜色、布局、letterbox 的差异 |
| 训练框架 vs ONNX Runtime（浮点） | 匹配框 IoU ≥ 0.99；置信度绝对差 ≤ 1e-3；类别一致率 100%；分数阈值以上无额外/遗漏框 | 同一模型导出，误差应很小 |
| letterbox 反算回原图 | 框角点误差 ≤ 1 像素（取整规则内） | 需要固定取整与补边参数 |
| 量化前后（冻结验证集） | mAP@0.5 绝对下降 ≤ 0.03；各类召回下降 ≤ 0.05；固定样本匹配率 ≥ 90%（IoU ≥ 0.5 且类别一致） | 检测对框回归更敏感；阈值待课堂需求确认 |
| 板端 vs 电脑参考 | 与量化后参考的匹配条件一致；另记录端到端延迟与内存 | 不能用“能出框/类别对”代替位置与置信度比较 |
| 板端实时性 | 帧率 ≥ 5 fps、端到端延迟 ≤ 200 ms（建议值，P8 前按课堂需求冻结） | 需同时记录分辨率、最大检测数、内存峰值 |
| 学生新样本效果 | 例如 20 张新图片中至少 75% 出现正确类别且 IoU ≥ 0.5 的检测（建议值，待冻结） | 应同时报告固定样本结果，但两者不能互相替代 |

验收配置必须包含：数据/标注摘要、类别表、模型结构、输入尺寸、预处理与后处理参数、固定样本集、测试集、匹配算法版本、各项阈值、目标机器/板卡/固件/转换器版本。配置本身版本化，并与产物 ID、清单 SHA-256 绑定。

### 6.4 失败与不可用规则

- 训练发布、电脑加载、转换发布、板端部署四个交接点都必须执行适用校验；失败时返回稳定错误码、阶段和位置，不静默使用默认参数继续。
- 任一步失败或取消：临时产物不发布、不加载、不登记为当前模型；失败原因和日志保留以便诊断，但状态必须是失败/未验证，不能显示为可用。
- 已发布包不原地修改；重新训练、重新导出、重新转换都生成新产物 ID，并保留来源关系。
- 转换记录、固定样本验证记录、板端验证记录分别保存并绑定产物 ID 与清单摘要；为补记一次板端验证不修改已发布模型包。
- 汇报中不得把“转换成功”“PC 仿真通过”“格式校验通过”写成“板端可用”或“课堂验收通过”。

## 9. 结论

- M3 检测课在当前仓库中**未实现**：没有检测标注、检测数据清单、检测训练/导出、检测电脑测试、转换产物或板端运行证据；只能确认分类 `1.0` 链路已实现并有本机测试记录，不能把分类能力外推到检测。
- 在无板卡条件下，P1（契约与版本决策）、P2（数据与标注格式草案）、P3（训练可行性实测）、P4/P5（后端与界面开发）可以先行；P6/P7 需要转换工具链但不需要板卡；P8/P9 必须实物 K230、目标机与课堂数据，不能由 Linux/开发机/仿真结果替代。
- 本机已完成两次**不训练的导出探测**（第 4.5 节，SSDLite 与 fasterrcnn 各一次）：两个候选都可 CPU 实例化并导出不含 NMS 的 ONNX（SSDLite：8.98 MB、1,481 节点、43 种算子；fasterrcnn：75.94 MB、1,515 节点、53 种算子且含 `RoiAlign`），导出图均含 `If` 控制流；输出名已按模型实际字典顺序声明（见第 4.5 节“输出命名说明”）。该结果只证明“两个候选的实例化/导出与算子清单”这一项前置事实，**不证明**可训练、可转换或可上板，也不改变检测未实现的状态。
- 本文不修改 [模型接口与产物契约](model-contract.md)、[K230 板端可行性准备](k230-feasibility.md) 或其他文档；检测扩展的字段、版本、阈值在 P1/P2 评审前均不冻结。
- 下一步建议：先由 lead 对 Q1～Q4、Q6、Q7 做出决定，再启动 P2；同时确认硬件与工具链提供时间，避免在 P6 才发现 M3 被外部条件阻塞。
