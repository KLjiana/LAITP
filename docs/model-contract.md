# 模型接口与产物契约

状态：首版开发约束，契约版本 `1.0`。本文定义后续实现必须满足的规则；分类契约的 Schema 与产物包校验器已实现并通过本机测试（见[契约校验说明](contract-validation.md)），但不代表端到端验收、转换或板端链路已经可用。

## 1. 目标与适用范围

适用于 WPF 界面、Python 训练与推理后端、电脑端推理运行时、K230/K210 转换器和板端程序之间的模型交接。

模型必须连同输入定义、输出解释、类别映射、运行要求和验证记录一起交付。接收方不得根据文件名、张量尺寸或开发者经验猜测模型语义。

本文中的“必须”是交付条件；“建议”允许在记录理由后采用其他方案。未满足强制条件的产物不能标记为可用或验证通过。

## 2. 模型产物包

每次训练或格式转换生成一个独立的产物包：

```text
model-package/
  manifest.json
  model.onnx                 # 示例；实际格式由清单声明
  labels.json
  validation/
    sample.png               # 示例；可以是多份样本或其他模态
    expected.json
```

- `manifest.json` 是唯一的产物入口，必须列出权重及其外部数据文件、标签、验证样本和参考结果的相对路径与 SHA-256。
- 路径以产物包根目录为基准。禁止绝对路径、目录穿越及通过符号链接访问包外文件。
- SHA-256 用于检查完整性和文件对应关系，不作为来源可信性的证明。
- `labels.json` 使用 UTF-8 有序字符串数组；数组下标就是类别 ID。禁止加载时排序或重新编号。
- 完成验证的包视为不可变。修改权重、标签或影响推理的契约内容必须产生新的 `artifact_id`。
- 训练、转换和验证中的文件写入临时目录。所有必要文件落盘并通过校验后，才整体发布到可选模型目录；失败或被取消的临时产物不得被加载。
- 模型、标签、预处理及后处理作为整体切换，不得分别替换。不能依赖原开发机的绝对路径、缓存或联网下载。

## 3. 清单字段

字段名称在实现 JSON Schema 时沿用本表。清单中缺失必填字段、字段互相矛盾或实际模型与清单不一致时，校验必须失败。

| 字段 | 要求 |
| --- | --- |
| `contract_version` | 必填，格式为 `major.minor`；当前为 `1.0` |
| `artifact_id` | 必填，全局唯一的产物 ID，每次训练或转换重新生成 |
| `task` | 必填，受支持的任务枚举；首版为 `image_classification`，检测为 `object_detection` |
| `provenance` | 必填，包含项目 ID、训练记录 ID、数据快照或清单摘要、生成时间；转换产物还包含来源产物 ID 和来源清单的 SHA-256 |
| `files` | 必填，列出包内载荷文件的路径、用途和 SHA-256；不包含清单自身，避免循环摘要 |
| `model` | 必填，模型入口文件、格式及格式版本；ONNX 还声明 opset 和外部数据文件 |
| `inputs` | 必填数组，逐个定义张量名称、形状、数据类型、布局和语义 |
| `outputs` | 必填数组，逐个定义张量名称、形状、数据类型和语义 |
| `preprocessing` | 必填，声明执行位置和有序处理步骤；即使无处理也须显式声明 |
| `postprocessing` | 必填，声明执行位置和有序处理步骤；不得使用含义不明的默认值 |
| `labels` | 分类和检测必填，包含标签文件路径及类别数量 |
| `runtime` | 必填，声明目标平台、运行时、版本兼容范围及所需能力；板端还声明已支持的板卡型号和固件范围 |
| `conversion` | 转换产物必填，记录转换器及版本、配置、量化方式和校准数据清单摘要；未量化也需显式声明 |
| `validation` | 必填，引用固定样本、参考结果和适用的验收阈值配置 |

数据快照或清单必须能够定位到本次训练实际使用的样本、标注、类别顺序及数据划分。项目中的样本被修改后，不能改变旧训练记录的含义。

验证执行记录单独保存并绑定 `artifact_id` 和清单摘要，避免为记录一次新的板端验证而修改已发布的模型包。

## 4. 输入、输出与处理规则

### 4.1 张量与图像输入

- 明确批次维、输入名称、形状、数据类型及 NCHW/NHWC 等布局。动态维度须声明允许范围，并确认目标运行时支持。
- 明确 RGB/BGR、灰度或其他通道语义，以及像素初始数值范围。
- 按执行顺序声明缩放、裁剪、补边、归一化、布局转换及批次维处理。
- 缩放必须明确拉伸、等比补边或裁剪方式，以及插值算法；补边必须明确位置、颜色和尺寸取整规则。
- 归一化必须给出精确公式、各通道参数及参数对应顺序，不能只写“标准归一化”。
- 需要精确复现时，明确解码方向处理、插值坐标与取整规则，并用参考输入张量校验跨运行时实现。

### 4.2 输出解释

- 分类模型必须明确输出是 logits 还是概率，以及类别轴和标签映射。需要 Softmax 时声明轴和执行位置。
- 检测模型必须明确输出是原始检测头还是已解码结果，记录必要的解码参数、置信度计算方式、框格式（如 `xyxy` 或 `cxcywh`）和坐标单位。
- 检测模型必须明确 NMS 是否在图中执行；图外执行时记录算法、类别处理方式、阈值和最大检测数量。
- 检测框必须明确对应原图、缩放后图像或模型输入坐标，并规定去补边和映射回原图的方法。
- 量化张量必须明确实际输入输出数据类型、scale、zero point，以及逐通道量化轴；不得假定量化模型仍使用浮点输入输出。

### 4.3 处理的执行位置

每个处理阶段必须声明由模型图、电脑端程序或板端程序执行。多方分别执行时，拆为有序阶段，逐段记录执行方。

同一个操作只能由约定的一方执行，禁止漏做或重复执行。例如，模型图已含 Softmax 或 NMS 时，外部程序不得再次执行。

以下为分类契约的**说明性片段**，不是可直接加载的完整清单。数值仅作示例，实际值必须由训练与导出配置生成：

```json
{
  "contract_version": "1.0",
  "task": "image_classification",
  "inputs": [
    {
      "name": "images",
      "shape": [1, 3, 224, 224],
      "dtype": "float32",
      "layout": "NCHW",
      "color_space": "RGB"
    }
  ],
  "preprocessing": {
    "executor": "host",
    "source_pixel_range": [0, 255],
    "steps": [
      {
        "op": "resize",
        "width": 224,
        "height": 224,
        "mode": "stretch",
        "interpolation": "bilinear"
      },
      {
        "op": "normalize",
        "formula": "(pixel * scale - mean) / std",
        "scale": 0.00392156862745098,
        "mean": [0.485, 0.456, 0.406],
        "std": [0.229, 0.224, 0.225],
        "channel_order": "RGB"
      },
      { "op": "transpose", "from": "HWC", "to": "CHW" },
      { "op": "add_batch_dimension", "axis": 0 }
    ]
  },
  "outputs": [
    {
      "name": "logits",
      "shape": [1, 3],
      "dtype": "float32",
      "meaning": "class_logits",
      "class_axis": 1
    }
  ],
  "labels": { "path": "labels.json", "count": 3 },
  "postprocessing": {
    "executor": "host",
    "steps": [{ "op": "softmax", "axis": 1 }]
  }
}
```

`host` 表示模型图之外的调用方，其具体实现由 `runtime` 限定。转换后执行位置或输入输出发生变化时，必须更新派生产物的契约。

## 5. 交接校验与可用状态

| 交接点 | 必须执行的检查 | 可声明的结果 |
| --- | --- | --- |
| 训练完成 | 清单结构、文件摘要、实际张量、类别映射及固定样本推理 | 训练产物可用 |
| 电脑加载 | 契约兼容性、文件摘要、任务类型、运行时能力和实际张量；首次在该运行环境加载时执行固定样本验证 | 当前电脑运行环境验证通过 |
| 模型转换 | 校验来源包；记录来源关系；重新读取转换后张量信息，验证预处理、后处理和量化配置 | 转换产物校验通过 |
| 板卡部署 | 设备、固件、运行时匹配；传输完整性；实际板端运行固定样本并与参考结果比较 | 当前板卡部署验证通过 |

转换器不提供模型元数据读取能力时，必须通过官方工具、运行时接口或实际验证建立等价证据，不能凭旧清单推定转换结果。

转换成功不等于板端验证通过。没有实物测试时，只能报告已完成的转换或模拟检查，板端状态必须保留为未验证。

失败时返回稳定的错误码、出错阶段、字段或文件位置及可操作的说明，不得静默采用默认参数继续运行。

## 6. 进程通信约束

C# 与 Python 使用 UTF-8、按行传输的 JSON 消息。标准输出仅承载协议消息，日志写入标准错误；接收方应限制单条消息大小。图像、权重及大数据通过受控文件路径传递。

消息信封必须包含：

| 字段 | 含义 |
| --- | --- |
| `protocol_version` | 进程通信协议版本，与模型契约版本独立维护 |
| `request_id` | 请求及对应响应的关联 ID |
| `project_id` | 所属项目 |
| `task_id` | 本次任务唯一 ID，重试时产生新 ID |
| `message_type` | 消息类型，如进度、结果、错误、取消确认 |
| `sequence` | 同一任务内由发送方维护的递增序号，用于识别重复或迟到消息 |
| `artifact_id` | 操作已有模型时必填；新模型生成前可为空，成功结果中必须填写 |
| `payload` | 由消息类型定义的结构化内容 |

- 界面必须核对项目、任务和请求归属，不接受旧任务更新当前进度或当前模型。
- 任务状态至少区分运行中、取消中、成功、失败和已取消；终态不能被迟到消息覆盖。
- 用户取消后，迟到的成功消息不得自动切换当前模型；未整体发布的产物按临时产物处理。
- 训练成功消息必须在产物包整体发布之后发送，并携带清单路径和摘要。
- 子进程退出、协议解析失败、未知必需消息类型和版本不兼容必须作为显式错误处理。

## 7. 版本与兼容性

- 改变字段含义、必填结构或处理语义时升级主版本；兼容的可选扩展升级次版本。
- 接收方必须声明支持的契约和协议版本。未知主版本直接拒绝；较新次版本只有在兼容策略明确允许且所需能力均受支持时才可接受。
- 未知操作、张量语义和必需能力不能被忽略。允许忽略的可选元数据须由 Schema 明确标识。
- 不自动猜测或隐式迁移旧模型。迁移必须显式执行、生成新产物、保留来源关系并重新验证。
- JSON Schema 是结构约束的唯一来源；C#、Python 和转换适配器不得各自维护互相矛盾的字段定义。Schema 无法表达的文件、运行时和语义校验由公共校验规则补充。

## 8. 端到端验证

使用同一组固定样本，按适用范围验证以下链路：

```text
训练框架推理 → 电脑端部署格式推理 → 转换后推理 → 实际板端推理
```

- 固定样本须关联可追溯的来源模型、预处理后的参考输入张量或摘要、原始输出及解释后的参考结果。
- 输入张量校验用于定位解码、颜色、布局和归一化差异；输出校验用于定位导出、量化和后处理差异。
- 验收阈值必须在运行验证前按任务、精度和设备确定并版本化。不得为使失败变成通过而临时放宽阈值。
- 分类检查输出误差、预测一致性及代表性验证集上的准确率变化；检测检查框位置、类别、置信度以及约定数据集上的检测指标变化。
- 量化前后允许合理误差，不能要求所有设备逐位相同，也不能只凭“模型能加载”判定正确。
- 少量固定样本用于交接冒烟验证，不能代替代表性验证集上的效果评估。
- 每次记录产物 ID、清单摘要、运行时、设备及固件版本、样本集、阈值配置、时间和实际结果。通过、失败、跳过及未执行必须分开报告。

## 9. 首版落地顺序

1. 定义分类模型与消息信封的 JSON Schema，建立有效及无效样例。
2. 实现文件完整性、路径、标签顺序、张量、版本及处理语义的校验器。
3. 在训练发布和电脑加载处接入校验，跑通固定样本的端到端检查。
4. 增加检测及 K230 契约扩展和板端验证，再接入 K210。

涉及契约的实现变更须同步更新文档、Schema、生产方、消费方及对应验证。文档或示例本身不得被当作功能已经完成的证据。
