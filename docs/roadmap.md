## 1. 产品目标

面向中小学生的离线 AI 教学平台，交付 Windows x64 桌面软件，做到解压双击、免注册、断网可用。学生能够自己采集数据、训练和测试小模型，并将适配的模型部署到 K230、K210 开发板。

以无独立显卡的机房电脑作为基础使用场景。模型规模、训练方式和课堂流程由目标机器的实际性能决定。检测训练和文生图另行验证资源需求，不提前承诺普通 CPU 电脑能够在一堂课内完成。

核心教学流程：

```text
提出问题 → 采集和检查数据 → 训练 → 使用新样本测试 → 分析误判 → 补充数据再训练
```

项目保存贯穿全过程。硬件课程在模型训练后增加转换、部署及真实板端测试。

## 2. 功能范围与优先级

| 优先级 | 实验 | 课堂流程 |
| --- | --- | --- |
| 第一阶段 | 图像分类 | 按类别拍照或导入图片，训练后用新图片和摄像头测试 |
| 第二阶段 | 目标检测与 K230 | 导入图片、画框、训练适配的 YOLO 模型，电脑测试后转换并在板端识别新样本 |
| 第三阶段 | K210 兼容 | 使用经过验证的专用网络和转换链，完成独立的硬件教学流程 |
| 第四阶段 | 声音分类 | 录制拍手、敲桌和背景音，训练后用麦克风实时测试 |
| 第四阶段 | 姿态识别 | 用预训练模型提取人体骨架，采集姿势并训练姿势分类器 |
| 后续按课程选择 | 拓展实验 | 离线 OCR、文生图、声纹识别、决策树和搜索算法 |

文生图先在教师机上测量出图时间、内存和显存需求，再决定采用学生操作、教师演示还是预设体验流程。声音与姿态优先于计算和分发成本更高的拓展实验。

首版暂缓账号、云同步、插件市场、自动更新、多项目并行训练和复杂调参。

## 3. 技术结构

| 模块 | 当前方向 | 责任 |
| --- | --- | --- |
| 桌面界面 | WPF、C#、XAML，采用 MVVM | 实验入口、采集、标注、数据检查、训练进度与结果预览 |
| AI 后端 | 内置 Python 子进程 | 训练、推理、导出及结构化进度和错误报告 |
| 任务管理 | 界面侧统一调度子进程 | 任务身份、取消、重试、退出检测及结果归属 |
| 项目管理 | 每个项目一个文件夹 | 样本、标注、配置、训练记录、模型产物及导出记录 |
| 模型契约 | JSON Schema 与语义校验器，契约 1.0 的分类 Schema 与校验器已实现 | 约束模型元信息、进程消息和端到端交接 |
| K230 转换 | YOLOv8 → ONNX → K230，具体版本待验证 | 目标板兼容检查、量化、转换及部署验证；前置条件与验证门槛见[K230 板端可行性准备](k230-feasibility.md)（规划，未实现） |
| K210 转换 | YOLOv3 → K210，具体网络与版本待验证 | 按板卡资源和算子限制提供独立适配 |
| 离线分发 | Windows x64 自包含 ZIP | 随包提供所需 .NET 运行时、Python、权重、原生依赖及可分发转换工具 |

所有模型交接与通信遵守 [模型接口与产物契约](model-contract.md)。本文负责规划范围和顺序，具体模型字段、兼容性及校验规则以契约为准。

实现原则：

- 摄像头由统一采集模块管理，避免 C# 与 Python 同时占用设备；预览使用有界队列，处理不及时则丢弃旧帧。
- 进程控制和结果采用按行 JSON；图像、权重及大数据通过受控文件路径传递。实时数据通道的吞吐在技术验证阶段实测。
- 主后端、K230 与 K210 转换链分别管理依赖，固定已验证的工具与模型版本。
- 学生界面显示实验步骤、进度和可操作的错误说明，技术参数与完整日志留给诊断界面。
- 数据修改与模型训练状态分开表示；新增样本后提示当前模型尚未使用这些样本。

## 4. 首版范围：跑通第一堂课

完整流程：

```text
新建项目 → 创建类别 → 拍照或导入 → 检查样本 → 训练
→ 新图片或摄像头测试 → 保存 → 退出 → 重新打开并继续
```

| 能力 | 首版要求 |
| --- | --- |
| 项目操作 | 新建、打开、保存、另存为和最近项目 |
| 样本操作 | 摄像头拍照、批量导入、删除及各类别数量提示 |
| 训练 | CPU 运行、进度反馈、取消、失败后重试 |
| 测试 | 单张图片与摄像头测试，显示预测类别及置信度 |
| 反馈 | 验证集表现、各类别表现和典型误判样本 |
| 错误处理 | 摄像头不可用、样本不足、磁盘空间不足、后端退出 |
| 保存恢复 | 保存样本、配置、训练记录和模型，重新打开后能继续测试和训练 |

分类训练优先验证“轻量预训练特征提取器 + 学生数据训练分类头”。后续再评估开放部分网络微调，不把从零训练深层网络作为首版前提。

训练集和验证集尽量按采集批次划分，避免相邻连拍图片分散到两侧造成准确率虚高。课堂测试引导学生换背景、距离和光照，使用未参与训练的新样本。

## 5. 项目数据组织

以下为建议结构，具体字段在实现项目格式时确定并版本化：

```text
学生项目/
  project.json              # 项目类型、格式版本、类别及当前模型引用
  data/
    images/                 # 原始样本；其他模态按需要增加目录
    annotations/            # 标签与检测框
    splits/                 # 训练与验证划分
  runs/
    <训练记录 ID>/
      config.json
      dataset-manifest.json # 本次数据、标签和划分的可追溯清单
      metrics.json
      model-package/        # 遵守模型契约的完整产物包
  exports/
    <导出记录 ID>/           # 派生产物包与转换记录
  validation-runs/          # 绑定产物摘要的验证执行记录
  logs/
```

项目使用相对路径，复制到另一台电脑后仍可打开。保存使用临时文件写入后替换，避免意外退出损坏已有记录。数据清单关联不可变快照或其他可恢复版本，后续修改样本不能改变旧训练记录的含义。

## 6. 开发里程碑

阶段按验收推进。K230 的高风险技术实验提前到 M0，完整课堂功能仍在分类流程稳定后开发。

| 阶段 | 工作内容 | 交付物与退出条件 |
| --- | --- | --- |
| M0：技术验证 | CPU 分类训练、摄像头推理、子进程通信、离线包试运行、K230 最小转换实验；建立分类契约 Schema 和校验器原型 | 有可复现命令、固定样本结果、性能记录和已知限制；确定分类技术基线，记录 K230 已验证组合或具体阻塞 |
| M1：第一堂课 | 分类采集、训练、测试、项目保存和契约校验接入 | 学生可在断网目标电脑上完成全流程，退出重开后继续；模型交接检查通过 |
| M2：课堂稳定性 | 取消与重试、设备与进程错误处理、保存恢复、依赖整理和打包 | 干净 Windows 机器无需预装开发环境即可解压运行，通过完整离线验收 |
| M3：K230 硬件课 | 图片标注、检测训练、电脑测试、量化转换、部署和结果展示 | 学生自训模型在指定板卡识别新样本，转换前后效果符合预定阈值；M0 的相关阻塞已解决 |
| M4：K210 兼容 | 验证专用网络与转换链，补充限制提示和板端运行流程 | 形成与 K230 分开的可复现教学流程，通过真实 K210 验收 |
| M5：扩展实验 | 先声音与姿态，再按课程需求引入其他实验 | 每个实验都有采集或输入、运行、反馈、保存和离线验收，并扩展相应契约 |

M0～M2 可在“一名全职开发者”的假设下先按 6～10 周作预算参考，不作为交付承诺；M0 实测后重新评估。板卡适配与拓展实验单独排期。

## 7. 硬件课程路线

创建检测实验时明确目标为电脑端、K230 或 K210，并提前约束模型结构和输入配置，避免训练结束才发现无法转换。

每个板端支持组合都要记录：具体板卡型号、固件版本、转换器版本、运行时、模型结构、输入尺寸、量化方案和后处理位置。现有 YOLO 转换路线仅作为适配起点，不代表同系列任意模型都受支持。

检测课（M3）的可行性规划见[检测课可行性规划](detection-feasibility.md)：契约扩展草案、标注格式、转换门槛、P1–P9 里程碑与开放问题均在文档中，**当前未实现**；其中 P1–P5 可在无硬件条件下先推进。P1/P2 的具体格式草案见[检测契约与格式草案](detection-contract-draft.md)（仍为草案，未激活），待决问题建议见[检测决策建议](detection-decisions.md)（建议稿，未决策）。

验收使用学生自己训练的模型和未参与训练的新样本，同时保留固定样本验证结果。不能用预训练演示模型的成功代替学生模型的部署验收，也不能用转换成功代替真实板端运行。

检测训练在普通 CPU 上耗时过长时，依据实测选择小数据微调、教师机训练或跨课时训练。先确认课堂可行性，再确定默认流程。

转换工具若不能在 Windows 离线环境运行或无法随包分发，须记录为相应硬件课的阻塞。可评估教师端离线转换方案，但必须明确其部署要求及对原有一体化流程的影响。

## 8. 性能与验收

M0 选定一台最低目标配置的机房电脑和一款具体 K230 板卡。固定数据规模、类别数、图像尺寸及版本，记录：

- CPU、内存、系统版本和可用磁盘空间。
- 冷启动时间、分类训练时间、峰值内存。
- 摄像头预览帧率、推理延迟和取消响应时间。
- ZIP 大小、解压后大小及运行时缓存占用。
- 转换耗时、板端延迟及转换前后效果变化。

根据课堂时长与 M0 结果制定后续验收阈值，在验收前固定测试配置和阈值，不在失败后临时放宽。

每个阶段保留可复现验证步骤，区分通过、失败、跳过与未执行。模型一致性验证的样本、误差及设备记录遵守模型契约。

## 9. 离线分发与平台验证

离线是各阶段的约束，不能只在最终发布时补做：

- 固定依赖、模型及转换工具版本，建立文件和许可证清单，确认再分发条件。
- 随包提供所需权重、配置、词表、运行时和原生库，排除首次运行自动下载。
- 验证中文路径、含空格路径、普通用户权限和可写缓存目录。
- 核心功能不依赖登录、联网校验或远端服务。

当前进展（2026-11-23）：已能生成开发期离线 ZIP；**精简完整包 278,932,704 B（约 266 MiB）**（内置便携 Python 与自包含桌面、不含 wheel，SHA-256 `b48bb0b6…39e51689`），本机验证 18,172 个文件摘要、包内 Python 依赖导入、推理、训练报告、启动脚本、桌面启动、首次运行自检与失败场景，并验证**包内现场自检**（`scripts/verify_offline_bundle.py --extracted .`）；在**中文/空格路径**下用包内 Python 走通“建项目 → 导入 → 检查 → 训练 → 发布 → 预测 → 项目校验”；另以清空 PATH/清除 Python 变量/不可用代理的方式模拟净环境，完整流程与桌面启动同样通过；界面经 Windows UI Automation 验证了窗口定位、自动自检、按钮点击、缺 Python 失败提示、新建项目 + 导入、批量导入、测试集导入、“打开项目 → 检查数据 → 训练并发布 → 预测”、关闭重开后的项目恢复、训练历史重新导出、项目编辑与严格验收失败提示（解包目录流程使用包内 Python）；摄像头**设备选择、检测刷新、拍照、连拍与高帧率预览**已用 DroidCam 虚拟摄像头验证（拍照约 0.3–0.8 s/张，连拍 3 张去重后新增 1，`MediaFrameReader` 预览约 20–21 fps，静态画面触发重复内容校验；见[摄像头能力](camera.md)），真实摄像头待验证；`scripts/verify_all.py --ui` 一键验证 **16 步全部通过**（约 10 分钟，报告写入 `artifacts/verify-all/`；摄像头自动化测试自 2026-11-18 起按要求停止，摄像头步骤记录为跳过）；真实数据课堂演练记录了单机时间预算（阶段合计约 16.0 s、含 30 张预测约 33.0 s，2026-11-20 复测；数字随负载波动，以 `artifacts/classroom-rehearsal/result.json` 为准，见[真实数据验证](real-data-validation.md)）。**汇总状态与外部阻塞见[项目状态报告](status-report.md)**；老师日常使用请先看[老师快速上手](teacher-quickstart.md)。仍未在干净 Windows 机器、普通用户权限与真正断网环境验收，详见[离线分发包](offline-bundle.md)与[目标机验收清单](acceptance-checklist.md)。

干净 Windows 机器的发布验收流程：

```text
断网 → 解压 → 双击 → 新建项目 → 采集 → 训练 → 测试
→ 保存 → 退出 → 重新打开 → 继续测试
```

Linux 云环境用于 Python 后端、协议、契约和适用的构建检查。Windows 测试机负责 WPF、摄像头、麦克风、原生依赖及离线包验证。K230、K210 功能分别在实物硬件验收。
